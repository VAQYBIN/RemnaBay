# 0071. Подготовка этапа 10: миграция

- **Дата:** 2026-10-16
- **Статус:** принято

## Контекст
Перед этапом 10 (миграция — блок 9) спека не отвечала на несколько вопросов. Часть из них появилась после разбора кода remnawave-tg-shop ([research/spike-bots-subscriptions.md](../research/spike-bots-subscriptions.md), раздел «Этап 10»):
- по каким платежам адаптер решает, что клиент «платил в старом боте» (решение 0070): у старого бота несколько провайдеров, возвраты не записываются, а поздние уведомления провайдера могут затереть успешный статус;
- как отмечать «Триал использован», если явной отметки триала в старом боте нет;
- каких пользователей панели усыновлять: в панели есть истёкшие и отключённые;
- что делать, если клиент открыл новый бот раньше, чем прошло усыновление;
- конфликт ли, если файл связывает клиента с пользователем панели без Telegram ID (9.12);
- дополняет ли импорт клиентов, которых усыновили без файла: решение 0070 говорит, что повторный импорт уже перенесённых пропускает;
- как оператор задаёт сопоставление тарифов, какой пробный прогон можно применить и что показывает отчёт;
- считать ли новым клиентом (1.17) клиента из файла, у которого нет пользователя в панели.

## Решение

### Адаптер remnawave-tg-shop
- **«Платил в старом боте: да»** — у клиента есть хотя бы один платёж в состоянии `succeeded` с суммой больше нуля. Провайдер любой, включая Звёзды Telegram и криптовалюту: клиент платил деньгами в любой форме.
  - В форке с веб-аккаунтами учитываются и платежи привязанного веб-аккаунта.
  - Подтверждение активации оплаченного тарифа в форке тоже считается оплатой: так не теряется оплата, статус которой позже затёрло уведомление провайдера.
  - Иначе — «Платил в старом боте: нет».
- **Чего по базе не видно**, и это принимается:
  - возвраты старый бот не записывает, вернувший деньги клиент остаётся «платившим»;
  - клиент, чей единственный платёж оспорен (chargeback), выходит «не платившим».
- **Клиенты, которых старый бот подтянул из панели синхронизацией**, приходят без истории платежей, хотя могли платить раньше. Сколько их у владельца, проверяется на копии данных. Если такие найдутся, адаптер не передаёт им поле «Платил в старом боте», и они считаются платившими (решение 0070). Признак выбирается по итогам проверки.
- **«Триал использован»** — если старый бот сейчас отказал бы клиенту в триале: у клиента есть любая запись подписки или активация триала. Неиспользованное разрешение на повторный триал в форке значит «не использован».
- **Подсказку тарифа** адаптер в MVP не передаёт. В форке у тарифов уже есть сквады и лимит устройств, и группы сопоставления почти совпадают с тарифами. Импорт подсказку принимает и показывает, если её передал другой адаптер.
- Клиенты форка без Telegram (веб-клиенты) в файл не попадают.

### Усыновление
- **Усыновляются все пользователи панели с Telegram ID**, в любом статусе: активные, исчерпавшие трафик, истёкшие и отключённые. Истёкший клиент видит свою подписку и продлевает её с прежней ссылкой.
- **Клиент уже есть в магазине** (открыл новый бот до усыновления): его пользователи панели становятся его подписками, клиент получает пометку «усыновлён». Подписки, которые у него уже есть, не меняются. В отчёте такие клиенты считаются отдельно.
- **Сопоставление тарифов — по группам.** Пробный прогон сам делит пользователей панели на группы: точный набор внутренних сквадов плюс лимит устройств. Для каждой группы показывается, сколько в ней пользователей. Оператор выбирает группе тариф или оставляет «без тарифа» и запускает пробный прогон снова.
  - «Параметры отличаются от тарифа» — сквады, лимит устройств, лимит трафика или его сброс не такие, как у выбранного тарифа.
- **Применить можно только последний пробный прогон своего вида** — усыновления или импорта — и только в течение суток после него. Применение заново читает панель с тем же сопоставлением и файлом; итоговый отчёт показывает, что получилось на самом деле.
- **Одновременно идёт один прогон миграции.**

### Импорт
- **Пользователь панели без Telegram ID**, с которым файл связывает клиента, — не конфликт. Он усыновляется по файлу, в панели ничего не меняется (9.6). В отчёте такие связи считаются отдельно.
- **Клиент, усыновлённый без файла,** при импорте получает данные из файла один раз: «Платил в старом боте», «Триал использован», реферальные коды, пригласившего. Так же дополняется клиент, который сам открыл новый бот до импорта. Клиенты, уже перенесённые из файла, пропускаются (9.7).
- **Перенесённый клиент** — усыновлённый или перенесённый из файла. Новым клиентом на главной (1.17) он не считается, даже если впервые открыл новый бот за выбранный период: он пришёл из старого бота.
- **Отчёт** показывает числа по каждой строке. Для конфликтов и нераспознанного он показывает ещё и список: Telegram ID, пользователь панели, причина. Экран миграции видит только владелец.

### Предложения агента
Приняты как способ реализации; при ревью этапа владелец может изменить.
> **Предложение (не утверждено):**
> - **Ключи JSON формата** — в [migration-format.md](../migration-format.md).
> - **Реферальный код** — значение параметра `start` целиком. Адаптер remnawave-tg-shop выдаёт для клиента `ref_u<код>`, `ref_U<код>`, `ref_<код>` и `ref_<Telegram ID>`: так выглядят ссылки, которые принимает старый бот. `ref_<код>` для кода из одних цифр не выдаётся: такую ссылку старый бот читает как Telegram ID. Новый бот сравнивает код точно.
> - **Язык** из файла сохраняется как есть, как язык из Telegram: если перевода на него нет, бот отвечает на языке по умолчанию (решение 0018), а появится перевод — клиент получит его.
> - **Дата появления** клиента, усыновлённого без файла, — самая ранняя дата создания его пользователей в панели.
> - **Название подписки:** первая — `subscription.default_name` («Основная»); следующие — новый текст `subscription.numbered_name` («Подписка {number}»). Если у клиента уже есть подписки, нумерация продолжается.
> - **Пригласивший**, которого нет ни в файле, ни в магазине, попадает в «не распознано». Существующую реферальную связь импорт не меняет.
> - **Конфликты (9.12):**
>   - пользователь панели уже привязан к другому клиенту;
>   - Telegram ID пользователя в панели — другой;
>   - реферальный код уже ведёт на другого клиента.
>
>   Не применяется только связь из файла. Пользователь панели с другим Telegram ID усыновляется по Telegram ID из панели, как без файла (9.4, 9.10). Если пользователя без Telegram ID в панели указали у двух клиентов файла, он не достаётся никому.
> - **Реферальные связи** — последний шаг применения. Если применение прервалось раньше, повторный импорт дописывает связи и уже перенесённым клиентам, остальные их данные не меняет.
> - **Telegram ID** — целое число больше нуля, которое помещается в базу; иначе запись попадает в «не распознано».
> - **Не распознано:**
>   - Telegram ID повторяется в файле — обе записи;
>   - ссылка на пользователя панели, которого нет;
>   - пригласивший, которого нет.

## Альтернативы
- **Не считать оплатой Звёзды или всё, кроме рублей** — отклонено: клиент, плативший Звёздами, всё равно платил.
- **Отмечать триал только по явным отметкам** — отклонено: в оригинале отметку затирает покупка, а в форке прошлые триалы отметок не получили; большинство реальных триалов потерялось бы.
- **Усыновлять только активных** — отклонено: истёкший клиент купил бы новую подписку с новой ссылкой вместо продления старой.
- **Клиент уже в магазине — конфликт** — отклонено: инструмента ручной привязки в MVP нет, клиент не увидел бы оплаченный в старом боте срок.
- **Пустой Telegram ID в панели — конфликт** — отклонено: файл старого бота знает, чей это пользователь, а панель при усыновлении не меняется.
- **Импорт полностью пропускает усыновлённых** (как в 0070) — отклонено: оператор, который сначала усыновил клиентов, а потом подготовил файл, потерял бы «Платил в старом боте», коды и пригласивших.
- **Сопоставление правилами, которые оператор пишет сам** — отклонено: дольше и легче ошибиться, а группы и так видны в отчёте.
- **Применять любой пробный прогон без срока** — отклонено: отчёт, по которому оператор принимает решение, может сильно устареть.
- **В отчёте только числа** — отклонено: разбираться с конкретными конфликтами оператору пришлось бы по файлу и панели вручную.
