# 0046. Шифрование секретов из админки: Fernet из `cryptography`

- **Дата:** 2026-10-05
- **Статус:** принято

## Контекст
Секреты, которые оператор вводит в админке (ключи платёжных провайдеров), хранятся в базе в зашифрованном виде; ключ шифрования лежит в `.env` ([04-operator-settings.md](../04-operator-settings.md), критерий 1.1). Не были выбраны алгоритм, библиотека и формат ключа — в `.env.example` стояло «требования к формату ключа появятся вместе с шифрованием».

## Решение
- **Рецепт Fernet из библиотеки `cryptography`** (pyca): AES-128-CBC с HMAC-SHA256, случайный вектор инициализации для каждого шифрования. Подделанный или зашифрованный другим ключом секрет не расшифруется — магазин получает понятную ошибку, а не мусор.
- **Формат ключа** — ключ Fernet: 32 байта в base64 (44 символа). Создаётся командой `remnabay generate-key` (в Docker: `docker compose run --rm --no-deps migrate generate-key`). Ключ неверного формата — магазин не запускается и подсказывает команду (1.1).
- Модуль `remnabay.crypto` шифрует и расшифровывает строки; где хранить зашифрованные настройки провайдеров, решают блоки 1 и 3.

## Альтернативы
- AES-256-GCM напрямую из `cryptography` — отклонено: нужно самим управлять nonce и форматом хранения; Fernet даёт то же без возможности ошибиться в деталях.
- Своя реализация на стандартной библиотеке — отклонено: в стандартной библиотеке Python нет симметричного шифрования.
- Ключ — произвольная строка-пароль с выводом ключа (KDF) — отклонено: лишняя сложность; оператор и так копирует ключ в `.env` один раз.

## Последствия
- Новая зависимость `cryptography` (Apache-2.0 / BSD), поддерживается pyca, колёса для amd64 и arm64.
- Смена ключа шифрования делает сохранённые секреты нечитаемыми. Поведение админки в этом случае — вопрос в [open-questions.md](../open-questions.md). Ротация ключа (MultiFernet) — при необходимости позже.
- Разработчикам: значение `ENCRYPTION_KEY` в локальном `.env` нужно заменить ключом из `remnabay generate-key`.
