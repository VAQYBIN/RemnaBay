# 0026. Развёртывание

- **Дата:** 2026-10-03
- **Статус:** принято

## Контекст
Позиционирование обещает один compose, минимум зависимостей и спокойные обновления. Операторы ставят магазин либо на сервер с панелью (там уже есть обратный прокси, чаще Nginx), либо на отдельный сервер — со своим прокси или без него. Часть операторов предпочитает Caddy.

## Решение
- **Один образ, две роли:** «веб» (админка и её API, вебхуки Telegram, панели и провайдеров, страница-переходник, проверка здоровья) и «воркер» (очередь задач, периодические задачи). Роль задаётся командой запуска.
- **Миграции — отдельный короткий шаг** перед стартом веба и воркера; процессы сами не мигрируют.
- **Один домен** с фиксированными путями: админка, API админки, вебхуки, страница-переходник, проверка здоровья.
- **Бот получает обновления через вебхук;** опрос — режим для разработки без публичного адреса.
- **PostgreSQL по умолчанию — в том же compose** со своим томом; внешний сервер указывается в `.env`.
- **Обратный прокси в образ не входит.** В репозитории — готовые варианты:
  - тот же сервер, что и панель, с её Nginx: блок для `nginx.conf` и подключение к общей Docker-сети;
  - тот же сервер с Caddy;
  - чистый сервер с Caddy (сертификаты получаются автоматически);
  - чистый сервер со своим Nginx и certbot.
- **Во всех примерах прокси:** заголовки `Host`, `X-Real-IP`, `X-Forwarded-For`, `X-Forwarded-Proto`; перенаправление с HTTP на HTTPS; лимит размера загрузки, достаточный для файла миграции и логотипа; таймауты.
- **Вебхук панели на том же сервере** идёт по внутренней Docker-сети, наружу этот адрес можно не открывать. Подпись проверяется всегда.
- **Образы** публикуются с номерами версий (без опоры на `latest`) для amd64 и arm64; к каждой версии — changelog.
- **Проверки здоровья** веба и воркера для автоматического перезапуска.
- **Резервное копирование** — ответственность оператора; в документации готовый рецепт и рекомендация делать копию перед каждым обновлением.

## Альтернативы
- Прокси (Caddy) внутри compose по умолчанию — отклонено: конфликт с прокси, который у оператора уже есть.
- Отдельные сервисы для бота, API и фронтенда (как в remnawave-tg-shop) — отклонено: больше сервисов и upstream без пользы.
- Миграции при старте каждого процесса — отклонено: риск одновременных миграций.
- Обновление без простоя — не нужно: Telegram и провайдеры повторяют вебхуки, пропущенное от панели ловит сверка, неподтверждённые оплаты находит запрос статуса (3.29). Короткий перезапуск ничего не теряет.

## Последствия
- Обновление для оператора: скачать новую версию образа и перезапустить; миграции проходят сами.
