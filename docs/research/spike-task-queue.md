# Эксперимент: очередь фоновых задач

**Статус:** проведён; решение — [0024](../decisions/0024-task-queue.md)

## Зачем
Очередь задач — основа обещания надёжности: применение платежей, повтор операций строго по порядку (4.14–4.17), планировщик напоминаний, сверка с панелью, рассылки после перезапуска. Владелец не работал с Procrastinate, поэтому решение принимается после проверки на практике, а не на словах.

## Кандидаты
- **A. Procrastinate** — очередь задач для Python поверх PostgreSQL: блокировки с сохранением порядка, повторы, периодические задачи. Проект ищет дополнительных мейнтейнеров — это риск.
- **B. Своя минимальная очередь** — таблица задач в PostgreSQL и выборка со `SKIP LOCKED`.

В обоих случаях очередь используется только через собственный интерфейс магазина («поставить задачу», «выполнить задачу»), чтобы её можно было заменить, не трогая сценарии.

Redis-очереди (arq, taskiq и т. п.) не рассматриваются: лишний сервис и окно между записью в базу и постановкой задачи, в котором теряются операции.

## Вопросы — одинаковые для обоих кандидатов
1. **Постановка в той же транзакции.** Задача ставится в одной транзакции асинхронной сессии SQLAlchemy с изменением данных; откат отменяет и задачу.
2. **Порядок.** Задачи с одним ключом (идентификатор подписки) выполняются строго по очереди при нескольких воркерах.
3. **Повторы.** Нарастающие интервалы, остановка после заданного времени, задача становится видимой как проваленная.
4. **Периодическая задача** раз в минуту не выполняется дважды при двух воркерах.
5. **Падение воркера посреди задачи** — задача не теряется и выполняется снова.
6. **Наблюдаемость** — как увидеть зависшие и проваленные задачи (нужно для «Требуют внимания»).
7. **Понятность кода** — насколько легко владельцу читать код каждого варианта.

## Как проводить
- Отдельная папка вне репозитория проекта, Claude Code.
- PostgreSQL в Docker.
- Для каждого вопроса — небольшой сценарий, который можно запустить и увидеть результат.
- Код после эксперимента не переносится в проект.

## Выводы

Проведён 2026-10-03. Стенд: Python 3.13, SQLAlchemy 2.1.3 (async, драйвер psycopg 3.3), PostgreSQL 18, Procrastinate 3.10.0, всё в Docker. Код лежит вне репозитория, в `~/code/spike-task-queue`; там же README с командами запуска. По каждому вопросу у каждого варианта свой сценарий: он запускает воркеры отдельными процессами и печатает «ожидали / получили».

| 2. Порядок по ключу | да | да |

### Ответы по вопросам

**1. Постановка в той же транзакции.**
- **A — да.** С версии 3.8 (апрель 2026) `task.configure(connection=...)` принимает чужое соединение. Из сессии SQLAlchemy его берём так: `(await (await session.connection()).get_raw_connection()).driver_connection`. Откат через исключение и через `rollback()` убирает задачу. Работающий воркер не видит задачу до коммита. Ограничение: в SQLAlchemy должен стоять драйвер psycopg 3 (`postgresql+psycopg://`), с asyncpg так не получится.
- **B — да.** Задача — обычная строка, которую добавляют через `session.add`. Все те же проверки проходят.

**2. Порядок.** Три подписки по пять операций, три воркера по два потока. Вторая операция одной из подписок дважды падает и уходит в повтор.
- **A — да** (через `lock=<ключ>`). **B — да** (через условие «нет более ранней незавершённой задачи с тем же ключом»).
- В обоих вариантах операции каждой подписки завершились строго по порядку и не пересекались. Пока вторая операция ждала повтора, следующие операции этой подписки тоже ждали. При этом разные подписки шли параллельно на разных воркерах.
- Контрольный запуск без ключа (`--no-key`) в обоих вариантах нарушает порядок, и проверки это ловят. Значит, тест действительно проверяет порядок.

**3. Повторы.** Первый повтор через 1 с, дальше интервал удваивается, окно 10 с. Ожидали попытки на 0, 1, 3 и 7 с, затем статус «провалена».
- **B — да.** Получили интервалы 1,1 / 2,0 / 4,1 с и статус `failed`. В строке задачи видны `last_error` и число попыток. Окно отсчитывается от момента постановки.
- **A — с оговорками.**
  - Встроенный `RetryStrategy` останавливается только по числу попыток. Окно по времени пришлось написать самому (`RetryWithin`, около 10 строк). Причём окно считается по сумме интервалов: момента первой попытки задача не знает, а метод синхронный, в базу из него не сходить.
  - Текст ошибки Procrastinate **не хранит**: в `procrastinate_jobs` нет такой колонки, в `procrastinate_events` — только типы событий и время. Понадобились своя middleware воркера и своя таблица (около 15 строк).
  - С интервалом опроса по умолчанию (`fetch_job_polling_interval` = 5 с) повторы, назначенные на время, запаздывают до 5 с: вместо 1, 2, 4 с получили 5, 5, 5 с, и окно растянулось до 15 с. При минутных интервалах это несущественно, но настройку стоит знать.
- **Общее (A и B):** после окончательного провала следующие задачи той же подписки выполняются. Нужно ли их останавливать — вопрос к продукту (см. `open-questions.md`).

**4. Периодическая задача.** Два воркера, период 5 с; на середине один воркер убиваем через kill -9. Отдельно прогнан режим с настоящей минутой (около 5 минут).
- **A — да.** Повторов одного слота нет, тики продолжаются после kill -9. Защиту даёт уникальный ключ «задача + время» в `procrastinate_periodic_defers`.
- **B — да.** Тот же результат: строка «имя + начало периода» вставляется с `ON CONFLICT DO NOTHING`.
- Особенности:
  - В Procrastinate секунды — **шестое, последнее** поле cron (`* * * * * */5`). Я сначала поставил их первым полем, и задача тихо запускалась раз в 5 минут.
  - При старте Procrastinate догоняет последний пропущенный слот, если тот не старше `max_delay` (по умолчанию 10 минут).
  - B пропущенные за время простоя слоты не догоняет. Для напоминаний это не важно: по [решению 0014](../decisions/0014-reminders-scheduler.md) задача сама досылает всё, что пора отправить.

**5. Падение воркера посреди задачи.**
- **B — да.** Воркер держит блокировку строки всё время выполнения задачи. После kill -9 PostgreSQL закрывает его соединение, блокировка снимается, строка остаётся `todo`, и задачу сразу берёт другой воркер. Убитая попытка не засчитывается, потому что её транзакция откатилась. SIGTERM: воркер доделывает текущую задачу и выходит.
- **A — без дополнительной настройки нет.** После kill -9 задача навсегда остаётся в статусе `doing` за мёртвым воркером. Хуже того, она блокирует все следующие операции этой подписки, потому что `lock` занят. Сама библиотека такие задачи не перезапускает. Помогает периодическая задача `retry_stalled_jobs` — рецепт из документации, 6 строк. С ней задача перезапускается после истечения heartbeat (по умолчанию 30 с плюс период проверки) и выполняется. Убитая попытка засчитывается в `attempts`. SIGTERM: воркер доделывает задачу и выходит.
- **Общее (A и B):** воркер завис (SIGSTOP, как при зависании процесса или обрыве сети), а потом ожил. Оба варианта отдают задачу другому воркеру: A — по heartbeat, B — по `idle_in_transaction_session_timeout`. Но **оживший воркер доделывает свою устаревшую попытку уже после следующей операции подписки.** В B изменения базы этой попытки откатятся, но то, что она успела сделать вовне (вызов панели), уже сделано. Значит, при любом варианте задачи обязаны быть идемпотентными и сверять состояние перед действием (4.15).
- **Оговорка B: долгие задачи.** Задача держит транзакцию и соединение всё время выполнения. Если она простаивает (например, ждёт ответа панели) дольше `idle_in_transaction_session_timeout`, PostgreSQL рвёт соединение и у **здоровой** задачи. Попытка при этом не засчитывается, и задача перезапускается бесконечно (сценарий 5.4). Лечится таймаутом задачи в Python (`asyncio.timeout`), который меньше таймаута простоя: тогда слишком долгая задача падает как обычная ошибка и попытка засчитывается (сценарий 5.5). Остаётся случай, когда задача роняет весь процесс воркера (нехватка памяти и т. п.): такая задача тоже будет перезапускаться без счёта попыток.

**6. Наблюдаемость.** Созданы задачи всех видов: проваленная, ждущая повтора, долго выполняющаяся, стоящая в очереди за другой задачей подписки и (для A) зависшая за мёртвым воркером. Каждую нашли SQL-запросом.
- **B — да.** Проваленные и ждущие повтора видны с текстом последней ошибки и числом попыток. Выполняющиеся и зависшие видны через `pg_stat_activity`: воркер подписывает соединение «job 〈id〉 〈задача〉», а время выполнения берётся из начала транзакции. Истории попыток нет — только последняя ошибка.
- **A — да, с оговоркой.** Статусы, `get_stalled_jobs()`, `list_jobs_async()` и история переходов в `procrastinate_events` (каждая попытка со временем). Текста ошибки нет — только через свою middleware. У воркеров нет имён, только id и heartbeat. Готового веб-интерфейса нет: есть админка для Django и консоль `procrastinate shell`. Для «Требуют внимания» запросы в любом случае пишем сами.

**7. Понятность кода.**
- **B:** вся очередь — один файл `queue.py`, 120 строк кода (150 с комментариями). «Поставить задачу» — 4 строки, выборка — один SQL-запрос, выполнение — одна функция. Понимать нужно четыре вещи из SQL: `FOR UPDATE SKIP LOCKED`, SAVEPOINT, условие порядка через `NOT EXISTS`, таймауты транзакции. Это короткий код, но каждая строка в нём несёт смысл: ошибку в нём легко не заметить, а исправлять её будем мы сами.
- **A:** своего кода около 50 строк: постановка в транзакции, повтор по времени, текст ошибки, оживление задач, запуск воркера. Но при отладке читать придётся саму библиотеку: около 4,3 тыс. строк Python и около 550 строк схемы с функциями PL/pgSQL, где и живёт логика выборки и блокировок. Плюс 38 миграций схемы, которые при обновлении библиотеки надо применять. Понятий заметно больше: App, Task, Job, JobContext, JobManager, коннектор, `lock` и `queueing_lock`, статусы и события, heartbeat, stalled-задачи, deferrer периодических задач, middleware.
- **Типизация:** код обоих вариантов проходит pyright в строгом режиме. Аргументы задачи при постановке не проверяются ни там, ни там. В A вызов `task.defer_async(...)` типизирован, но для постановки в транзакции с ключом нужен `configure(...)`, и после него типы аргументов теряются.

### Подводные камни
- **Порядок — это порядок `id`, а не порядок коммитов (A и B).** Если две транзакции одновременно ставят задачи одной подписке, `id` может достаться не тому, кто закоммитил первым. Поэтому перед постановкой задачи нужно блокировать строку подписки.
- **Задачи должны быть идемпотентными (A и B):** «оживший» воркер может доделать устаревшую попытку (вопрос 5).
- **A:** без `retry_stalled_jobs` задача упавшего воркера висит вечно и блокирует подписку; это нужно помнить и настраивать.
- **A:** текст ошибки и окно повторов по времени — свой код; повторы по времени запаздывают на интервал опроса.
- **A:** постановка в транзакции работает только с драйвером psycopg 3 и опирается на возможность, появившуюся в 3.8 (апрель 2026).
- **A:** схему Procrastinate нужно встроить в миграции Alembic и обновлять вместе с библиотекой. Проект ищет мейнтейнеров, хотя выпуски идут: 3.8 — апрель, 3.9 — июнь, 3.10 — сентябрь 2026.
- **B:** каждая выполняющаяся задача держит транзакцию и соединение: пул соединений должен быть не меньше числа параллельных задач. Пока задача ждёт панель, строки, которые она уже изменила, остаются заблокированными.
- **B:** нужны два согласованных таймаута (задачи в Python и простоя в PostgreSQL); ошибка в их соотношении даёт бесконечный перезапуск.
- **B:** задача, которая роняет процесс воркера, перезапускается без счёта попыток.

### Что не проверялось
Нагрузка и производительность; очистка завершённых задач (в A для этого есть встроенная задача `remove_old_jobs`, в B её нужно писать); перезапуск самого PostgreSQL; LISTEN/NOTIFY в B (там опрос каждые 0,2 с); встраивание схемы Procrastinate в Alembic.

### Рекомендация
> **Принято** ([решение 0024](../decisions/0024-task-queue.md)) с дополнительными доработками: вариант **B — своя очередь**, при условии что до переноса в проект в неё добавлены таймаут задачи и проверка соотношения таймаутов (уже есть в эксперименте), блокировка подписки при постановке и очистка старых задач.
>
> Обоснование:
> - Все 7 вопросов B закрывает сам. A три вопроса (3, 5, 6) закрывает только с дописанным кодом, а самый опасный случай — задача упавшего воркера висит и блокирует подписку — по умолчанию выключен.
> - Весь код B помещается в один файл на знакомом владельцу SQLAlchemy. Его можно прочитать целиком и проверить ревью. В A ключевая логика спрятана в функциях PL/pgSQL библиотеки.
> - В B изменения базы, сделанные задачей, и отметка о выполнении фиксируются одной транзакцией: повтор не даёт двойного эффекта в базе.
> - Нет зависимости от проекта, который ищет мейнтейнеров.
>
> Чем платим:
> - Долгие задачи держат транзакцию; таймауты нужно настраивать аккуратно.
> - Нет готовой истории попыток, отмены и приоритетов.
> - Ошибки в этих ~120 строках — наша ответственность.
>
> Если на практике окажется много долгих задач (например, рассылки), это повод пересмотреть выбор. Поскольку очередь используется только через интерфейс магазина, замена не затронет сценарии.

Решение принято владельцем — см. [0024](../decisions/0024-task-queue.md).
