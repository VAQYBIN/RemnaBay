# Поведение панели Remnawave

Факты, на которые опирается спека. Проверено по исходникам бэкенда (github.com/remnawave/backend, коммит от 2026-09-12) и на живой панели.

## Сброс трафика
- **Не сбрасывать** — счётчик не обнуляется.
- **Раз в день** — каждую ночь по времени сервера панели.
- **Раз в неделю** — по понедельникам.
- **Раз в месяц** — первого числа календарного месяца, у всех одновременно.
- **Раз в месяц (от даты создания)** — в день месяца, соответствующий дате создания пользователя. Если такого числа в месяце нет — в последний день месяца. Первый сброс — не раньше чем через месяц после создания.
- Дату создания можно передать только при создании пользователя; изменить её через API нельзя.
- Дату следующего сброса API пользователя не отдаёт; её нужно вычислять по стратегии и дате создания.
- Массовое действие «сбросить трафик всем» обнуляет счётчик у всех пользователей, включая тех, у кого стратегия «не сбрасывать».

## Статусы
- При исчерпании трафика пользователь получает статус LIMITED, панель отправляет вебхук.
- При повышении лимита пользователь сразу возвращается в ACTIVE, дополнительных действий не нужно. *(проверено на живой панели)*

## Устройства (HWID)
- При включённом лимите устройств панель отправляет вебхуки `user_hwid_devices.added` и `user_hwid_devices.deleted` с данными пользователя и устройства. При выключенном — не отправляет.
- Список всех устройств в API есть, но его фильтры рассчитаны на фронтенд и дорогие для БД. Поэтому магазин ведёт собственный реестр устройств по вебхукам, а не ищет по панели.
- По словам автора, почти все операторы используют лимит устройств.

## События пользователя (вебхуки)
- Всегда: `user.created`, `user.modified`, `user.deleted`, `user.revoked`, `user.disabled`, `user.enabled`, `user.limited`, `user.expired`, `user.traffic_reset`, `user.first_connected`.
- `user.bandwidth_usage_threshold_reached` — при достижении порогов расхода трафика, настроенных в панели.
- `user.expiration` и `user.not_connected` — только если включены соответствующие параметры в `.env` панели. Поэтому магазин не опирается на них и ведёт напоминания об истечении сам.

## Подпись вебхуков
- Панель подписывает вебхуки: заголовки `X-Remnawave-Signature` и `X-Remnawave-Timestamp`. Магазин проверяет подпись и отклоняет неподписанные события.

## Уведомления об истечении в панели
- Включаются в `.env` панели: `EXPIRATION_NOTIFICATIONS_ENABLED` и `EXPIRATION_NOTIFICATIONS` — список смещений в часах от −744 до 744, не больше пяти до истечения и пяти после.
- Раз в минуту панель ищет пользователей, у которых дата окончания со смещением попадает ровно в текущую минуту, и отправляет `user.expiration` со смещением в данных события.
- Пропущенная минута (панель перезапускалась) не восстанавливается.

## Доставка вебхуков
- Панель повторяет неудавшуюся отправку вебхука 3 раза с интервалом 5 секунд, после чего событие отбрасывается. Если магазин недоступен дольше ~15 секунд, событие теряется. Поэтому магазин не должен полагаться на то, что получит каждое событие, и периодически сверяется с панелью.

## Идентификация
- Telegram ID у пользователя необязателен и не уникален: у нескольких пользователей может быть один Telegram ID.

## Дата окончания
- Дата окончания обязательна.
- Клиентские приложения показывают подписку с датой окончания в 2099 году как «бессрочную». Ориентир — именно 2099 год. *(со слов автора, по опыту)*
