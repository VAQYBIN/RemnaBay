# Вход в админку через Telegram OpenID Connect

**Статус:** выполнено (2026-10-06): исследование по источникам и эксперимент на тестовом боте @rbtest_123_bot. Решение — [0053](../decisions/0053-telegram-oidc-login.md).

## Зачем
Владелец хочет заменить вход в админку (1.4): сейчас — ссылка на бот с кодом подтверждения и кнопка `login_url` на `/admin` ([решение 0051](../decisions/0051-stage-4-refinements.md)); предлагается — «Log In With Telegram» по OpenID Connect. Нужно понять, подходит ли OIDC Telegram нашей схеме: каждый оператор разворачивает магазин на своём домене со своим ботом, в админку входит только команда, участник определяется по Telegram ID.

## Что установлено по источникам

**OIDC у Telegram официально есть.**
- Документация: https://core.telegram.org/bots/telegram-login. Появилась около конца февраля 2026 (по архиву страницы); отдельного анонса нет.
- Discovery: https://oauth.telegram.org/.well-known/openid-configuration, issuer `https://oauth.telegram.org`.
- Эндпоинты: авторизация `/auth`, токен `/token`, ключи `/.well-known/jwks.json`. UserInfo нет.

**Поток.** Только Authorization Code с PKCE (S256), то есть серверный обмен кода на токены. Обмен проходит с `client_secret_basic` или `client_secret_post` — ровно наша схема: бэкенд проверяет ID token и выдаёт свою HttpOnly-сессию.

**Регистрация.**
- Делается в мини-приложении @BotFather → бот → Login Widget: Allowed URLs (origin и точный redirect URI), Client ID и Client Secret.
- `client_id` — ID бота. `client_secret` — **отдельный секрет**, не токен бота.
- Одобрение Telegram не нужно. `/setdomain` для OIDC не нужен; адресов можно указать несколько.

**Telegram ID пользователя — в claim `id`, а не в `sub`.**
- `sub` непрозрачен и не равен ID пользователя: так в официальном примере, и так наблюдали на живых ботах.
- `id` приходит со scope `profile`, поэтому запрашивать нужно `openid profile`.
- Если подпись ID token — EdDSA или ES256K, scope `profile` недоступен и `id` не придёт: в BotFather нужно оставить RS256 или ES256.

**Проверка ID token.**
- Подпись по JWKS (кэш, повторное чтение при неизвестном `kid`).
- Белый список алгоритмов RS256 и ES256.
- `iss`; `aud` равен ID бота — сравнивать строками.
- `exp` и `iat` с небольшим допуском; `nonce`.
- Ошибку токен-эндпоинта искать в теле ответа: он отвечает 200 с `{"error": …}`.

**Старый способ.** Login Widget назван «legacy», но `login_url` в Bot API жив (Bot API 10.3) и по-прежнему требует `/setdomain`.

Подробности и ссылки на все источники — в отчёте исследования этапа 4 (сессия 2026-10-06); ключевые: официальная страница выше, discovery и JWKS, SocialiteProviders PR #1495 (проверено на живом боте), better-auth-telegram, Хабр 1033632.

## Что не подтверждено и проверяется экспериментом
Эксперимент — на тестовом боте @rbtest_123_bot. Код — `spikes/telegram_oidc/spike.py`; в проект он не переносится (CLAUDE.md).

Как проводится:
1. До включения OIDC: в @BotFather задать боту домен (`/setdomain`) и проверить вход по кнопке `login_url` на `/admin`.
2. В мини-приложении @BotFather → бот → Login Widget добавить разрешённые адреса: адрес магазина, `…/spike/oidc/callback`, `…/api/admin/auth/telegram/callback`. Отдельно попробовать `http://localhost:8000/…` (вопрос 7). Подпись — RS256. Client Secret положить в `.env` как `TELEGRAM_LOGIN_CLIENT_SECRET`.
3. Снова проверить `/setdomain` и кнопку `login_url` (вопрос 1).
4. Запустить скрипт на месте веба. Войти в настольном браузере, затем отказаться от входа, затем открыть ссылку во встроенном браузере Telegram и в мобильном браузере (вопросы 2–6). Скрипт пишет результаты в `results.json` (не в git).

1. Включение OIDC в @BotFather необратимо и выключает `/setdomain` и `login_url`? Если да, кнопка `login_url` на `/admin` перестанет работать.
2. Какой claim несёт Telegram ID на нашем боте: `id` (строка или число), и совпадает ли он с ID из `getUpdates`?
3. Сколько живёт ID token: в документации 3600 с, наблюдали 30 с.
4. Возвращается ли `nonce` в redirect-потоке.
5. Как Telegram сообщает об отказе пользователя на callback (`error=`?).
6. Работает ли поток во встроенном браузере Telegram и в мобильных браузерах; что видит пользователь (подтверждение в приложении, QR, вход по номеру).
7. Принимается ли `http://localhost` как redirect URI (для разработки) — по сторонним данным нет, нужен туннель.

## Выводы эксперимента
Четыре входа на @rbtest_123_bot: браузер на компьютере, вход после отказа, встроенный браузер Telegram, браузер на телефоне.

1. **Включение OIDC в @BotFather необратимо** — BotFather сам об этом предупреждает. Кнопка `login_url` на `/admin` и после включения работает (домен в `/setdomain` остался).
2. **Telegram ID — в claim `id`, строкой** (`"728763367"`), и совпадает с `OWNER_TELEGRAM_ID`. `sub` от `id` отличается. Claims при scope `openid profile`: `iss`, `aud`, `sub`, `iat`, `exp`, `nonce`, `id`, `name`, `given_name`, `family_name`, `preferred_username`, `picture`.
3. **ID token живёт 30 секунд** (`exp − iat = 30`, `expires_in = 30`). Обмен кода выполняется сразу; допуск по часам нужен небольшой.
4. **`nonce` возвращается и совпадает.** `aud` — строка, равна ID бота. Подпись RS256, ключ `oidc-1`, проверка по JWKS проходит.
5. **Отказ от входа не возвращает на сайт:** страница Telegram снова предлагает войти, параметра `error` на адрес возврата нет. Незавершённая попытка просто истекает.
6. **Как выглядит вход.** На странице Telegram — выбор аккаунта и «Продолжить с Telegram» (или вход по номеру телефона). Затем в приложении Telegram — окно «Авторизация на <домен>» с устройством и IP-адресом, кнопки «Авторизоваться» и «Отклонить». После подтверждения браузер сам возвращается на сайт. Одинаково работает в браузере на компьютере, во встроенном браузере Telegram и в браузере на телефоне. На странице Telegram показываются имя и аватар бота — значит, бота магазина нужно оформить брендом оператора.
7. **Повторный заход на адрес возврата** с тем же `state` возможен (браузер открыл страницу ещё раз). Попытка одноразовая; если сессия уже открыта, нужно вести в админку, а не показывать ошибку.
8. **`http://localhost`** не проверен. При разработке вход идёт через туннель (ngrok); запасной вход через бот работает и без OIDC.

В @BotFather настройки входа такие: **Redirect URIs** — точные адреса возврата; **Trusted Origins** — адреса сайта для запросов токена из браузера (нашему серверному потоку не нужны, но указываются); **Native Login**; **Signing Algorithm** (RS256 по умолчанию).
