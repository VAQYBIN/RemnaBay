# Эксперимент: rich-сообщения и даты в Telegram

**Статус:** проведён 2026-10-04 (этап 1 из [plan.md](../plan.md), часть «Telegram»); решения по предложениям — [0044](../decisions/0044-rich-messages-refinements.md)

## Зачем
[Решение 0017](../decisions/0017-bot-format.md) делает инструкцию по подключению, выбор тарифа и карточку подписки rich-сообщениями, а живое меню держит в одном сообщении. Формату несколько месяцев; до реализации экранов нужно знать его пределы и поведение в клиентах.

## Вопросы
1. **Лимиты.** Хватит ли пределов rich-сообщения (кнопки, блоки, объём текста) на инструкцию с несколькими платформами из конфига Subscription Page (блок 12)?
2. **Живое меню.** Можно ли отредактировать обычное сообщение в rich и обратно (`editMessageText`)?
3. **`date_time`.** Показывается ли дата в часовом поясе клиента?
4. **Отображение.** Как rich-сообщения и новые кнопки выглядят на Telegram Desktop, Android и в вебе (Web A, Web K), и что видят старые клиенты?

## Как проводить
- Источник — официальная документация Bot API 10.3 (core.telegram.org/bots/api, журнал изменений) на 2026-10-04.
- Живые проверки — отдельный чистый тестовый бот (без вебхука, создан для эксперимента); сообщения уходят только в личный чат владельца. Токен — в файле вне репозитория.
- Запросы к Bot API — напрямую по HTTP, чтобы видеть точный JSON и тексты ошибок. Код — вне репозитория, в `~/code/spike-telegram`; в проект не переносится.
- Инструкция собирается из встроенного конфига Subscription Page по умолчанию (исходники панели 3.4.4), язык — русский.
- Ручные проверки в клиентах (Desktop, Android, Web) проводит владелец. iOS и старые версии клиентов владельцу недоступны.

## Выводы

### Коротко

| Вопрос | Ответ |
|---|---|
| 1. Лимиты | Хватает с большим запасом. Инструкция по 12.3 из конфига по умолчанию — 88 блоков из 500 и ~4,3 тыс. символов из 32 768; даже все приложения всех платформ — 268 блоков и ~15,4 тыс. символов. Пределы документации подтверждены точно |
| 2. Живое меню | Bot API разрешает правку одного сообщения обычное → rich → обычное → rich и смену клавиатуры у rich. Во всех клиентах сообщения пришли к нужному конечному состоянию |
| 3. `date_time` | Клиенты показывают дату в местном часовом поясе и на своём языке. Но Android **не форматирует дату внутри rich** — показывает текст-подложку, а полную дату только по нажатию |
| 4. Отображение | Desktop, Android, Web A показывают rich-сообщения и новые кнопки. **Web K** не показывает rich-сообщения с рядом кнопок и обычные сообщения с неактивной кнопкой — вместо них заглушка «This message is currently not supported on Telegram Web». Старые клиенты, со слов владельца, показывают похожую заглушку «обновите приложение» |

Стенд: Bot API 10.3, запросы напрямую по HTTP; aiogram 3.31 (`__api_version__ = "10.3"`) тоже поддерживает `send_rich_message` и блоки rich. Клиенты владельца — Telegram Desktop, Android, Web A, Web K; часовой пояс владельца — UTC+5. iOS и старые версии клиентов не проверялись.

### Подробно

#### 1. Лимиты
Пределы из документации Bot API («Rich Message Limits») подтверждены пробами — граница точная, ошибка на единицу больше:

| Предел | Проходит | Ошибка за пределом |
|---|---|---|
| Блоков, включая вложенные | 500 | `RICH_MESSAGE_BLOCKS_TOO_MANY` |
| Символов текста (кириллица) | 32 768 | `RICH_MESSAGE_TEXT_TOO_LONG` |
| Кнопок в одном ряду (`buttons`) | 8 | `RICH_MESSAGE_BUTTONS_TOO_MANY` |
| Уровней вложенности | 16 | `RICH_MESSAGE_DEPTH_INVALID` |

- Рядов кнопок может быть много: 100 рядов по 8 кнопок прошли (ограничивает только число блоков).
- Под rich-сообщением работает обычная инлайн-клавиатура (`reply_markup`); 101 кнопка прошла.
- Инструкция собрана из встроенного конфига Subscription Page: платформа — сворачиваемый блок (`details`), внутри приложение, шаги (заголовок, описание, ряд кнопок), кнопка «Другие приложения»; под сообщением — «Скопировать ссылку», «Открыть в браузере», «Главное меню».
  - по 12.3 (рекомендуемое приложение): 88 блоков, 33 кнопки, ~4 337 символов;
  - все приложения всех платформ: 268 блоков, 75 кнопок, ~15 421 символ.
- Клиенты сворачивают длинное rich-сообщение под «Показать ещё» / «Show more» / «Read More».

**Попутно — конфиг по умолчанию.** Рекомендуемых (`featured`) приложений у платформы может быть несколько или ни одного: у Linux — ни одного, у Windows — три, у macOS и Android — по два. Критерий 12.3 говорит об одном рекомендуемом приложении.

#### 2. Живое меню
- Цепочки правок одного сообщения через `editMessageText` (`text` ↔ `rich_message`) и `editMessageReplyMarkup`: обычное с кнопками → rich → обычное → rich; rich → обычное → rich; смена только клавиатуры у rich. Все шаги — `ok`.
- В Desktop, Android, Web A и Web K обе цепочки показаны в конечном состоянии (rich-карточка с клавиатурой). Смена в реальном времени глазами не наблюдалась.
- Нажатия на кнопки внутри rich приходят боту обычными `callback_query`; в `message` есть `rich_message`.

#### 3. `date_time`
- Одна точка времени (10.10.2026 18:00 UTC) у владельца в UTC+5 показана как 23:00 во всех клиентах, в обычном сообщении и в rich — то есть в местном времени клиента. Язык — язык клиента (Web A — английский, Desktop и Android — русский).
- **Android внутри rich** (в абзаце и в ячейке таблицы) показывает текст-подложку как есть, подсвеченным; по нажатию — полная дата в местном времени. В обычном сообщении Android форматирует дату.
- Расхождения между клиентами: относительный формат `r` для одной даты — «через 5 дней» (Desktop, Web K) и «через 6 дней» (Android, Web A); формат `D` на Desktop — без года («10 октября»), на Web A — с годом.

#### 4. Отображение
| | Desktop | Android | Web A | Web K |
|---|---|---|---|---|
| Rich: заголовки, таблицы, сворачиваемые блоки, подвал, моноширинный текст | да | да | да | да |
| Rich с рядом кнопок (`buttons`) — любой стиль, неактивная кнопка | да | да | да | **заглушка** |
| Инструкция (ряды кнопок внутри сворачиваемых блоков) | да | да | да | показана; что внутри блоков — не проверено |
| Обычное сообщение: цветные кнопки, копирование | да | да | да | да |
| Обычное сообщение с неактивной кнопкой (`disabled`) | да | да | да | **заглушка** |
| Инлайн-клавиатура с `force_reply` | поле ответа открывается | да | да | не проверено |

- Заглушка Web K — «This message is currently not supported on Telegram Web. Try getdesktop.telegram.org»; сообщение целиком не видно, включая кнопки.
- У `InputRichMessage` нет запасного текста для клиентов без поддержки rich: бот не может задать, что увидит такой клиент.
- Ответ на сообщение с `force_reply` приходит боту с `reply_to_message` — магазин может сопоставить ответ с запросом (Web A и Android проверены).

## Предложения по спеке

Решения владельца 2026-10-04 — [решение 0044](../decisions/0044-rich-messages-refinements.md): первые два предложения отклонены (на Web K магазин не ориентируется), третье принято в изменённом виде.

> **Отклонено:** действия в rich-экранах — кнопками под сообщением. В выборе тарифа и карточке подписки кнопки действий ставить в обычную инлайн-клавиатуру под сообщением, а не рядами внутри rich: тогда эти экраны видны в Web K. Внутри rich кнопки остаются только в инструкции (шаги приложений), где без них не обойтись.

> **Отклонено (неактивные кнопки остаются):** неактивные кнопки ([решение 0017](../decisions/0017-bot-format.md)). Обычное сообщение с неактивной кнопкой Web K не показывает целиком. Варианты: не использовать неактивные кнопки (недоступное действие просто не показывается или объясняется текстом), или принять, что Web K у части клиентов показывает заглушку.

> **Принято в изменённом виде** (запасной текст — в часовом поясе магазина с подписью «МСК»; подсчёт дней не нужен — в текстах бота нет относительных дат): даты в rich. Android внутри rich показывает текст-подложку `date_time`, поэтому подложка должна быть понятной сама по себе: дата во времени магазина с явной пометкой (например, «01.11.2026 23:00 МСК»). Число оставшихся дней магазин считает сам, а не формат `r`: клиенты округляют его по-разному.
