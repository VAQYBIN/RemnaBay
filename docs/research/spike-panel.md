# Эксперимент: проверки на панели

**Статус:** идёт (этап 1 из [plan.md](../plan.md), часть «Панель»)

## Зачем
Ответы влияют на реализацию следующих этапов: клиент панели (этап 2), инструкция по подключению (блок 12), миграция (блок 9). Проверяется до того, как код на них опирается.

## Вопросы
1. **Конфиг Subscription Page пользователя.** Отдаёт ли панель по API-токену готовый ответ «пользователь → конфиг Subscription Page», или магазин определяет конфиг сам: внешний сквад пользователя → его конфиг, без сквада — конфиг по умолчанию (12.1)? Что происходит, если у сквада конфиг не задан?
2. **«Открыть в браузере» при запрете браузерам.** Что видит клиент по кнопке «Открыть в браузере» (12.6), если в панели правилами ответов браузерам запрещён показ Subscription Page? Отдельно — Telegram Desktop, Android и Web.
3. **Идентификаторы пользователя в панели v3.** По какому идентификатору адресуются пользователи в запросах и вебхуках панели 3.4.4 (ID, UUID, короткий идентификатор) и верно ли это описано в спеке ([migration-format.md](../migration-format.md)).
4. **SDK `remnawave-api` и httpx.** SDK требует `httpx>=0.27.2,<0.28`; на этапе 0 тесты FastAPI переведены на `httpx2`, потому что на него перешёл TestClient Starlette 1.7. Приемлем ли этот обходной путь надолго, или по [решению 0028](../decisions/0028-panel-client.md) пора переходить на свой клиент за тем же интерфейсом? Разбирают ли модели SDK 3.4.5 реальные ответы панели 3.4.4?

## Как проводить
- Источники: исходники бэкенда панели (тег 3.4.4), Subscription Page (8.0.0) и SDK `remnawave-api` (3.4.5).
- Живые проверки — на **рабочей** панели владельца (3.4.4): тестовой панели нет. Поэтому:
  - создаются только свои объекты с меткой `rbtest_` в имени (пользователи, внешний сквад, конфиг Subscription Page) и удаляются после проверок;
  - объекты, существовавшие до проверок, и глобальные настройки (правила ответов и т. п.) не меняются — только читаются;
  - список всех пользователей панели не запрашивается.
- Код эксперимента — вне репозитория, в `~/code/spike-panel`; в проект не переносится. Доступ к панели — из файла вне репозитория.
- Ручные проверки в Telegram (Desktop, Android, Web) проводит владелец.

## Выводы

Разбор исходников проведён 2026-10-04: бэкенд панели — тег `3.4.4` (коммит `b22970c`), Subscription Page — тег `8.0.0`, SDK `remnawave-api` — тег `v3.4.5`. Пути к файлам ниже — от корня соответствующего репозитория. Пометка *(живая панель)* — подтверждено на рабочей панели владельца; без пометки — по исходникам.

### 1. Конфиг Subscription Page пользователя

**Готовый запрос есть, но отвечает не полностью.**
- `GET /api/subscriptions/subpage-config/{shortUuid}` с обязательным JSON-телом `{"requestHeaders": {...}}` возвращает `{subpageConfigUuid: uuid | null, webpageAllowed: boolean}` (`libs/contract/commands/subscriptions/subpage/get-subpage-config-by-shortuuid.command.ts`).
- Вызывается обычным API-токеном со скоупом `subscriptions:subpage-config` (или шире). Особого токена нет: само приложение Subscription Page ходит в панель с таким же токеном.
- Принимает только `shortUuid`; по `id` пользователя — сначала `POST /api/users/resolve` или `GET /api/users/{id}`.

**`null` означает три разных случая, и ответ их не различает:** у пользователя нет внешнего сквада; у сквада не задан конфиг; пользователь не найден. Это один SQL-запрос «пользователь → внешний сквад → `subpageConfigUuid`» (`src/modules/users/repositories/users.repository.ts`, `getUserSubpageConfigUuid`).

**Конфиг по умолчанию выбирает не панель, а приложение Subscription Page** (`backend/src/modules/webpage/webpage.service.ts`, `getFinalSubpageConfigUuid`):
- у конфига по умолчанию фиксированный uuid `00000000-0000-0000-0000-000000000000` и имя `Default`; удалить его нельзя, менять содержимое можно; панель создаёт его заново при старте, если его нет;
- если в `.env` приложения Subscription Page задан `SUBPAGE_CONFIG_UUID` (отличный от нулевого), **все** пользователи получают этот конфиг, сквады не учитываются. Магазин эту переменную не видит.

**Кэш приложения.** Subscription Page загружает все конфиги один раз при старте и больше не обновляет (`webpage.service.ts`). Конфиг, созданный или изменённый после старта, веб-страница покажет только после перезапуска приложения — а магазин по API увидит сразу.

**Что это значит для 12.1.** Магазин может определить конфиг сам: запрос выше (или цепочка «пользователь → внешний сквад → `subpageConfigUuid`»), а при `null` — конфиг `00000000-0000-0000-0000-000000000000`. Расхождение с веб-страницей возможно в двух случаях: оператор задал `SUBPAGE_CONFIG_UUID` в Subscription Page или не перезапустил её после правки конфига.

*Живая проверка — в работе.*

### 2. «Открыть в браузере» при запрете браузерам

**Как панель решает, показывать ли страницу.**
- Правила ответов проверяются по порядку, срабатывает первое совпавшее; если не совпало ни одно — ответ 403 (`src/modules/subscription-response-rules/`). Условия бывают только по заголовкам запроса.
- Типы ответа для запрета: `BLOCK` (403), `STATUS_CODE_404`, `STATUS_CODE_451`, `SOCKET_DROP` (обрыв соединения).
- Тип `BROWSER` на самом бэкенде отдаёт JSON с данными подписки, а не HTML. HTML отдаёт приложение Subscription Page, если оно стоит перед панелью (ссылка подписки ведёт на его домен).

**Что делает Subscription Page с браузером** (`backend/src/modules/subscription/subscription.controller.ts`, `backend/src/modules/webpage/webpage.service.ts`):
- браузер распознаётся по User-Agent (`Mozilla`, `Chrome`, `Safari` и т. п.);
- приложение спрашивает у панели `webpageAllowed` с заголовками клиента; `webpageAllowed` истинно, только если правила дали `BROWSER`;
- если `false` — приложение **рвёт соединение** (`socket.destroy()`), без HTTP-ответа. Так же оно поступает, если подписка не найдена или панель ответила ошибкой.

**Следствие.** При запрете браузерам клиент не видит ни страницы, ни сообщения — только ошибку браузера или обратного прокси перед Subscription Page (какую именно — зависит от прокси оператора). Без Subscription Page (ссылка ведёт прямо на панель) — ответ 403/404/451 с JSON или обрыв.

**Как проверить на живой связке, ничего не меняя.** Для браузера несуществующая подписка и запрет правилами проходят один и тот же путь — обрыв соединения. Поэтому то, что увидит клиент, проверяется ссылкой на несуществующую подписку на домене Subscription Page оператора; правила ответов не трогаются.

**Магазин может узнать заранее.** Тот же запрос `subpage-config` возвращает `webpageAllowed` для переданных заголовков.

*Живая проверка — в работе.*

### 3. Идентификаторы пользователя в панели v3

- Поля `uuid` у пользователя в 3.4.4 нет: его удалила миграция `20260720132335_drop_user_uuid`.
- Пользователь адресуется числовым `id` (автоинкремент): `GET/DELETE /api/users/{id}`, действия `/api/users/{id}/actions/...`, устройства `/api/hwid/devices/{userId}`, массовые операции — `userIds` (до 500).
- Уникальны также `shortUuid` и `username`; `telegramId` не уникален.
- `PATCH /api/users` принимает в теле `id` или `username`.
- `POST /api/users/resolve` по одному из `id`, `shortUuid`, `username` возвращает все три.
- Ссылка подписки — `https://{SUB_PUBLIC_DOMAIN}/{shortUuid}`. Отзыв подписки (`revoke`) меняет `shortUuid` (если не передан `revokeOnlyPasswords`) и всегда — пароли и `vlessUuid`.
- В вебхуках `user.*` и `user_hwid_devices.*` — полный пользователь (`id`, `shortUuid`, `username`, `telegramId`, `externalSquadUuid`, …); у устройства — `userId`.

**Расхождение со спекой.** В [migration-format.md](../migration-format.md) пользователи панели перечисляются как «UUID и/или короткий идентификатор» — в панели 3.4.4 UUID пользователя нет.

### 4. SDK `remnawave-api` и httpx

**Почему `httpx<0.28`.**
- Ограничение шаблонное (каретка Poetry `^0.27.2`), а не из-за реальной несовместимости. SDK не использует ничего, что удалено в httpx 0.28, и одинаково работает на httpx 0.27.2, 0.28.1 и httpx2: проверено на подставном транспорте — создание, чтение, изменение и удаление пользователя, ответы 404, 502, обрыв соединения.
- Настоящая привязка — к `rapid-api-client==0.6.0` (ноябрь 2024). SDK импортирует его внутренние классы и переопределяет приватные методы; с версиями 0.7–0.10, где httpx уже новый, импорт SDK падает с `ImportError`.
- Задач и запросов на слияние про httpx 0.28 или httpx2 нет ни в репозитории SDK, ни у `rapid-api-client`. Мейнтейнер SDK по сути один.

**httpx и httpx2.**
- Линия httpx 0.x не развивается: последний выпуск — 0.28.1 (декабрь 2024), дальше только предварительные 1.0.dev.
- httpx2 — форк httpx 0.28.1, который ведёт Pydantic (с мая 2026). Импортируется как `httpx2` и уживается с httpx в одном окружении; TestClient Starlette с версии 1.2 берёт типы из него.
- Известных уязвимостей у httpx 0.27.2 нет. Но в августе 2026 для httpx2 опубликованы исправления трёх проблем, унаследованных от httpx: одновременные `Content-Length` и `Transfer-Encoding`, внедрение заголовков в multipart, неограниченная распаковка ответа. Те же места без исправлений есть в httpx 0.27.2. Для магазина риск низкий: панель — доверенный сервер, multipart магазин не использует.

**Качество SDK для магазина.**
- Под pyright strict: 23 ошибки на пробе в 35 строк. Пакет без `py.typed`; методы возвращают `модель | str | bytes | Response`; конструкторы части моделей pyright считает неполными. Каждый вызов в обёртке потребует `cast`.
- Сетевые ошибки выходят наружу сырыми `httpx.ConnectError`: обработка в SDK — мёртвый код.
- Нельзя обнулить поле: тело собирается с `exclude_none=True`, поэтому `externalSquadUuid=None`, `telegramId=None`, `description=None` просто не отправляются.
- Новое значение перечисления в ответе (например, новый статус пользователя) ломает разбор ответа целиком.
- Мелкие расхождения с контрактом 3.4.4: лимит массовых операций 1000 против 500 в панели, длина `shortUuid` при отзыве, устаревшие скоупы `*:by-uuid`.
- Модель конфига Subscription Page в SDK не описана (`config: Any`) — её придётся писать самим при любом варианте.

**Тесты.** SDK принимает готовый `httpx.AsyncClient`, поэтому его HTTP подменяется через `httpx.MockTransport`. respx с httpx2 не работает; pytest-httpx с SDK не ставится.

**Другие зависимости стека.** aiogram (aiohttp), yookassa (requests) и `fastapi[standard]` с SDK не конфликтуют; nalogo (чеки, v1) тянет `httpx>=0.25`. Попутно: aiogram 3.31 ограничивает `pydantic<2.14`.

**Объём своего клиента.** MVP нужны 16 запросов к панели плюс проверка подписи вебхуков. Оценка — 400–600 строк: транспорт, около 15 моделей, вебхуки. OpenAPI-спецификацию каждой версии панели можно взять из образа `remnawave/backend:<версия>` (`/opt/app/openapi.json`).
