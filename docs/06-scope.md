# 6. Объём версий и критерии приёмки

**Статус:** 🟡 нарезка собрана, критерии приёмки не начаты

## Версии
([решение 0015](decisions/0015-mvp-definition.md))
- **MVP** — минимум, с которым автор переводит на проект свой действующий магазин.
- **v1** — минимум для публичного релиза, когда проект не стыдно показать сообществу.
- **Потом** — всё остальное; идеи живут в [backlog.md](backlog.md).

## Данные с первого дня
Модель из [01-domain.md](01-domain.md) реализуется в MVP целиком, даже если функции поверх неё отложены. Откладываются экраны и действия, но не данные. Пометка «данные — MVP, функция — v1» означает: MVP хранит и поддерживает эти данные, а интерфейс появится в v1.

## Нарезка

### Ядро и надёжность
| Фича | Этап | Почему |
|---|---|---|
| Ядро, бот, базовая веб-админка | MVP | Без этого нет продукта |
| Вход через Telegram, первый владелец из `.env` | MVP | Иначе в админку не попасть |
| Чек-лист первичной настройки | MVP | Автор настраивает с нуля |
| Режим «магазин скоро откроется» | MVP | Часть первичной настройки |
| Журнал действий | MVP | Основа обещания надёжности |
| Вебхуки панели с проверкой подписи, сверка, повтор операций | MVP | «Деньги пришли — услуга будет» |
| Разбор «оплачен, не применён» | MVP | Там же |

### Клиент
| Фича | Этап | Почему |
|---|---|---|
| Первая покупка, продление | MVP | Ядро магазина |
| Тариф «срок + безлимит» | MVP | Модель автора |

| Реестр устройств | данные — MVP | Иначе проверке триала не на что опереться |
| Отзыв триала по устройству, чёрные списки | v1 | У автора злоупотреблений нет, у сообщества есть |

| Точка расширения проверок триала | потом | |

## Критерии приёмки
Каждая фича MVP получает проверяемые утверждения вида «если X, то Y». Фича готова, когда выполнены все её критерии. Задача агенту выдаётся как одна фича с её критериями.

```
### Фича: название
- **Версия:** MVP / v1 / потом
- **Сценарии:** ссылки на 02-scenarios.md
- **Критерии приёмки:**
  - [ ] Если ..., то ...
```

## Блоки MVP
Фичи MVP сгруппированы в блоки — каждый блок является законченной задачей для агента. У каждого критерия есть номер: на него ссылаются тесты, задачи и обсуждения.

| # | Блок | Критерии |

### Блок 3. Покупка и продление, контракт провайдера, ЮКасса
- **Версия:** MVP
- **Сценарии:** «Первая покупка подписки», «Продление подписки и докупка пакета» (в MVP — только тариф «срок + безлимит»)
- **Вне блока:** промокоды (блок 8), бонусы и смешанная оплата (v1), смена тарифа с перерасчётом (v1)

#### Каталог
- [ ] **3.1** Если тариф в продаже, он показывается клиенту в списке тарифов.
- [ ] **3.2** Если тариф в архиве, он не показывается в списке тарифов, но доступен для продления подписки, у которой он сейчас, пока подписка активна.

#### Первая покупка
- [ ] **3.3** Если клиент без подписок выбрал тариф, он видит экран подтверждения: тариф, срок, цена, итог к оплате.
- [ ] **3.4** Если клиент нажал «Оплатить», создаётся счёт у провайдера на сумму с экрана подтверждения, и клиент переходит к оплате.
- [ ] **3.5** Если клиент дважды нажал «Оплатить» на одном экране подтверждения, создаётся один счёт.
- [ ] **3.6** Если провайдер подтвердил оплату, в панели создаётся ровно один пользователь с параметрами тарифа (срок, лимит устройств, сквады), подписка магазина связывается с ним, платёж переходит в «применён», клиент получает ссылку на подписку и инструкцию по подключению.
- [ ] **3.7** Если оператор изменил цену или параметры тарифа после создания счёта, применяются условия на момент создания счёта.
- [ ] **3.8** Если клиент не оплатил счёт за время его жизни, счёт истекает и подписка не создаётся.
- [ ] **3.9** Если провайдер подтвердил оплату по истёкшему счёту, подписка создаётся, как по действующему.
- [ ] **3.10** Если клиент создал новый счёт, не оплатив старый, старый счёт отменяется в магазине (и у провайдера, если провайдер это поддерживает).
- [ ] **3.11** Если оплачены оба счёта одной покупки, первая применённая оплата создаёт подписку, а вторая продлевает её на срок своего тарифа; команда получает уведомление.
- [ ] **3.12** Если провайдер отклонил оплату, клиент видит сообщение об этом и может попробовать снова; подписка не создаётся.
- [ ] **3.13** Если клиент заблокировал бот до сообщения об успехе, подписка всё равно создаётся, а недоставка записывается в журнал.
- [ ] **3.14** Первая подписка получает название по умолчанию.
- [ ] **3.15** Если новый клиент впервые открыл бот по реферальной ссылке, записывается реферальная связь. Если клиент уже существовал, ссылка ведёт на него самого или он усыновлён, связь не записывается.
- [ ] **3.16** Если у клиента есть триальная подписка, покупка применяется к ней: пользователь панели и ссылка прежние; оплаченный срок добавляется к оставшимся дням триала; лимит устройств и сквады устанавливаются по тарифу.

#### Продление
- [ ] **3.17** Если подписка активна, новая дата окончания — прежняя дата окончания плюс срок тарифа.
- [ ] **3.18** Если подписка истекла, новая дата окончания — момент подтверждения оплаты плюс срок тарифа.
- [ ] **3.19** При продлении пользователь панели и ссылка подписки не меняются.
- [ ] **3.20** Если тариф подписки в архиве, а подписка активна, продление доступно по текущей цене тарифа.
- [ ] **3.21** Если подписка истекла, а её тариф в архиве, продление этим тарифом недоступно; клиент может выбрать любой тариф в продаже, и он применяется к этой же подписке.
- [ ] **3.22** Если подписка истекла, пока клиент платил, продление считается от момента подтверждения оплаты.
- [ ] **3.23** Если у клиента одна подписка, «Продлить» сразу ведёт к ней, без выбора подписки.
- [ ] **3.24** Если у клиента несколько подписок (например, после усыновления), каждая показывается отдельно со своим названием, а продление доступно с экрана конкретной подписки.

#### Отрезки срока (данные для v1)
- [ ] **3.25** Каждое применённое продление или покупка добавляет к подписке отрезок срока со стоимостью, равной фактически оплаченной сумме.
- [ ] **3.26** Срок триала добавляется отрезком нулевой стоимости.

#### Контракт провайдера
- [ ] **3.27** Сценарии покупки и продления работают с провайдером только через контракт: создать счёт, принять подтверждение оплаты, запросить статус счёта, отменить счёт. Подключение нового провайдера не требует изменений в сценариях.
- [ ] **3.28** Платёж считается оплаченным только после подтверждения провайдера, проверенного по правилам этого провайдера. Непроверенное подтверждение отклоняется и записывается в журнал.
- [ ] **3.29** Если подтверждение от провайдера не дошло, магазин узнаёт об оплате, периодически запрашивая статус незавершённых счетов.
- [ ] **3.30** Если провайдер недоступен при создании счёта, клиент видит сообщение «Оплата временно недоступна, попробуйте позже»; ничего не создаётся.

#### ЮКасса
- [ ] **3.31** ЮКасса реализована через контракт провайдера (3.27) и проходит критерии 3.4–3.12 и 3.28–3.30.
- [ ] **3.32** После оплаты клиент возвращается в бот.

### Блок 4. Надёжность: вебхуки, сверка, повтор операций, журнал
- **Версия:** MVP
- **Сценарии:** «Реакция на изменения в панели», «Повтор неудавшихся операций», «Разобрать платёж «оплачен, не применён»»; сквозные правила 1–4

#### Вебхуки панели
- [ ] **4.1** Если подпись вебхука неверна или отсутствует, событие отклоняется и записывается в журнал.
- [ ] **4.2** Если одно и то же событие пришло повторно, его эффект применяется один раз.
- [ ] **4.3** Если в панели увеличили дату окончания, магазин добавляет к подписке отрезок нулевой стоимости.
- [ ] **4.4** Если в панели уменьшили дату окончания, магазин срезает отрезки с конца.
- [ ] **4.5** Если в панели изменили лимиты или сквады, магазин принимает их как факт.
- [ ] **4.6** Если пользователя удалили в панели, подписка помечается удалённой: клиент её больше не видит, история платежей сохраняется, событие записано в журнал.
- [ ] **4.7** Если подписку отключили в панели, клиент видит «Подписка отключена, обратитесь в поддержку». Если включили — снова видит обычное состояние.

#### Сверка с панелью
- [ ] **4.8** Магазин периодически сверяет состояние всех подписок с панелью. Если вебхук не дошёл, расхождение обнаруживается при следующей сверке и исправляется по тем же правилам, что 4.3–4.7.
- [ ] **4.9** Журнал показывает, каким путём магазин узнал об изменении: вебхук или сверка.
- [ ] **4.10** Если событие обнаружено сверкой с опозданием, его последствия для клиента применяются, только если ещё актуальны.

#### Недоступность панели
- [ ] **4.11** Если панель недоступна, оплаты принимаются и остаются в состоянии «оплачен, не применён» до её восстановления.
- [ ] **4.12** Если панель недоступна, клиент видит последние известные данные с пометкой, что они могут быть неактуальны.
- [ ] **4.13** Если панель недоступна дольше заданного времени, команда получает уведомление.

#### Повтор операций
- [ ] **4.14** Если операция (применение платежа, создание подписки, удаление устройств) не выполнилась из-за ошибки, система повторяет её с нарастающими интервалами в течение заданного времени.
- [ ] **4.15** Повтор не даёт двойного эффекта.
- [ ] **4.16** Незавершённые операции продолжаются после перезапуска магазина.
- [ ] **4.17** Операции над одной подпиской применяются строго в том порядке, в котором возникли.
- [ ] **4.18** Каждая попытка записывается в журнал.

#### «Оплачен, не применён»
- [ ] **4.19** Если платёж оплачен, но не применён сразу, клиент получает сообщение «Оплата получена, подписка создаётся».
- [ ] **4.20** Если автоматические попытки исчерпаны, платёж появляется в списке «Требуют внимания», на главной странице админки виден счётчик, команда получает уведомление.
- [ ] **4.21** Карточка такого платежа показывает клиента, что должно было примениться, историю попыток и текст ошибки.
- [ ] **4.22** Участник команды может применить платёж повторно, применить его созданием новой подписки или отметить решённым вручную. Отметка вручную требует комментария.
- [ ] **4.23** Если провайдер прислал подтверждение оплаты, которой магазин не знает, она появляется в «Требуют внимания» с пометкой «неизвестный платёж», команда получает уведомление.
- [ ] **4.24** После решения клиент получает уведомление о результате.

#### Журнал
- [ ] **4.25** Каждое изменение подписки и платежа и каждое ручное действие команды записывается в журнал: кто (участник команды, клиент, система, панель или провайдер), что, когда, над чем, с каким результатом.
- [ ] **4.26** Записи журнала нельзя изменить или удалить через админку.
