# 6. Объём версий и критерии приёмки

**Статус:** ✅ нарезка и критерии приёмки MVP утверждены; критерии v1 — позже

## Версии
([решение 0031](decisions/0031-stages-refined.md), уточняет 0015)
- **MVP** — первая рабочая версия: автор разворачивает её на тестовом сервере и проверяет на реальной панели.
- **v1** — версия, на которую автор полностью переводит свой магазин; одновременно публичный релиз.
- **Потом** — всё остальное; идеи живут в [backlog.md](backlog.md).

## Данные с первого дня
Модель из [01-domain.md](01-domain.md) реализуется в MVP целиком, даже если функции поверх неё отложены. Откладываются экраны и действия, но не данные. Пометка «данные — MVP, функция — v1» означает: MVP хранит и поддерживает эти данные, а интерфейс появится в v1.

## Критерии приёмки
Каждая фича MVP получает проверяемые утверждения вида «если X, то Y». Фича готова, когда выполнены все её критерии. Задача агенту выдаётся как одна фича с её критериями.

```
### Фича: название
- **Версия:** MVP / v1 / потом
- **Сценарии:** ссылки на 02-scenarios.md
- **Критерии приёмки:**
  - [ ] Если ..., то ...
```

Фичи MVP сгруппированы в блоки — каждый блок является законченной задачей для агента. У каждого критерия есть номер: на него ссылаются тесты, задачи и обсуждения.

### Блок 1. Первичная настройка и вход в админку
- **Версия:** MVP
- **Сценарии:** «Первичная настройка»; правила входа — «Участник команды» в [01-domain.md](01-domain.md)
- **Вне блока:** приглашение помощников и смена ролей (v1)

#### Запуск
- [ ] **1.1** Если в `.env` не задан обязательный параметр (токен бота, адрес и токен API панели, база данных, Telegram ID первого владельца, публичный адрес магазина, ключ шифрования), магазин не запускается и сообщает, какого параметра не хватает.
- [ ] **1.2** Telegram ID из `.env` при каждом запуске гарантированно является владельцем: если его нет в команде, он добавляется; остальные владельцы не удаляются. Это и первый вход, и путь восстановления доступа.
- [ ] **1.3** Модель команды хранит роль участника; в MVP единственный участник — владелец из `.env`.

#### Вход
- [ ] **1.4** На странице входа участник нажимает «Войти через Telegram», бот присылает ему подтверждение; после подтверждения в боте в браузере открывается сессия. Участник команды может войти и по кнопке, которую бот присылает в ответ на скрытую команду `/admin`; остальным на `/admin` бот отвечает как на непонятное сообщение.
- [ ] **1.5** Подтверждение входа одноразовое и действует ограниченное время.
- [ ] **1.6** Если вход пытается выполнить Telegram-аккаунт, не входящий в команду, вход отклоняется.

#### Чек-лист
- [ ] **1.7** Пока магазин не открыт, админка показывает чек-лист с состоянием каждого пункта: подключение к панели, вебхук панели, лимит устройств в панели, бренд, тарифы, способ оплаты, контакт поддержки, триал, миграция. Пункт «Триал» информационный и всегда выполнен: включён триал или нет — оба варианта нормальны.
- [ ] **1.8** Пункт «Подключение к панели» выполнен, если API панели отвечает с токеном из `.env` и версия панели совместима. Если версия несовместима, показывается требуемая версия.
- [ ] **1.9** Пункт «Вебхук панели» показывает адрес и секрет, которые нужно указать в панели, и становится выполненным после получения первого события с верной подписью.
- [ ] **1.10** Если в панели выключен лимит устройств, пункт показывает предупреждение, что защита триала по устройству работать не будет. Пункт не блокирует открытие магазина.
- [ ] **1.11** Пункт «Бренд» выполнен, когда заданы название и логотип (у приветственного текста есть значение по умолчанию).
- [ ] **1.12** Пункт «Миграция» необязателен и ведёт к запуску усыновления или импорта (блок 9).

#### Открытие магазина
- [ ] **1.13** Пока магазин не открыт, бот на любое сообщение отвечает «Магазин скоро откроется» — кроме участников команды и тестировщиков (1.21): для них бот работает как обычно.
- [ ] **1.14** Кнопка «Открыть магазин» становится доступна, когда выполнены обязательные пункты: подключение к панели, хотя бы один тариф в продаже, хотя бы один способ оплаты. Магазин открывается по нажатию владельца.
- [ ] **1.15** Чек-лист остаётся на главной странице админки, пока в нём есть невыполненные пункты.
- [ ] **1.21** Владелец задаёт в настройках список тестировщиков — Telegram ID, для которых бот работает как обычно, пока магазин закрыт.
- [ ] **1.22** Владелец может закрыть открытый магазин. Пока он закрыт: новые покупки, продления и триалы недоступны, клиент видит «Магазин временно закрыт», но свои подписки, ссылки и инструкции видит по-прежнему; уже пришедшие оплаты применяются как обычно; напоминания приостанавливаются. Для команды и тестировщиков бот работает как обычно.

#### Админка на телефоне
- [ ] **1.16** Вход, главная, поиск клиента, карточка клиента, выдача дней, «Требуют внимания» и карточка платежа пользуются на экране шириной 360 пикселей без горизонтальной прокрутки.

#### Цифры на главной
- [ ] **1.17** Владелец видит на главной: число активных платных подписок и отдельно — активных триалов; новых клиентов (впервые открыли бот за период, без усыновлённых), выручку и число оплат за выбранный период; число подписок, истекающих в ближайшие 3 дня, с переходом к их списку.
- [ ] **1.18** Период выбирается: сегодня, 7 дней, 30 дней. Периоды и даты в админке считаются в часовом поясе магазина (настройка).
- [ ] **1.19** Выручка за период — сумма применённых платежей за период минус возвраты, выполненные за период; бонусная часть платежей (v1) в выручку не входит.
- [ ] **1.20** Помощник (v1) цифр выручки не видит.

### Блок 2. Тарифы и их архивация
- **Версия:** MVP
- **Сценарии:** раздел «Тариф» в [01-domain.md](01-domain.md); решения 0009, 0011
- **Вне блока:** типы с квотой и пакетами, закрытие тарифа и преемник (v1)

- [ ] **2.1** Владелец создаёт тариф типа «срок + безлимит»: название, описание, срок в днях, цена, лимит устройств, сквады.
- [ ] **2.2** Сквады выбираются из списка, полученного из панели.
- [ ] **2.3** Модель тарифа хранит тип; в MVP в админке доступен только «срок + безлимит».
- [ ] **2.4** Владелец задаёт порядок тарифов в списке, который видит клиент.
- [ ] **2.5** Изменение параметров тарифа не меняет действующие подписки: новые параметры применяются при следующей покупке или продлении.
- [ ] **2.6** Изменение цены тарифа не влияет на уже созданные счета (см. 3.7).
- [ ] **2.7** Владелец переводит тариф в архив и может вернуть его в продажу.
- [ ] **2.8** Тариф, у которого есть или были подписки, нельзя удалить — только архивировать. Тариф без подписок удаляется.
- [ ] **2.9** Если владелец архивирует последний тариф в продаже, админка предупреждает, что новые клиенты не смогут ничего купить.
- [ ] **2.10** Изменения тарифов применяются без перезапуска магазина.

### Блок 3. Покупка и продление, контракт провайдера, ЮКасса
- **Версия:** MVP
- **Сценарии:** «Первая покупка подписки», «Продление подписки и докупка пакета» (в MVP — только тариф «срок + безлимит»)
- **Вне блока:** промокоды (блок 8), бонусы и смешанная оплата (v1), смена тарифа с перерасчётом (v1)

#### Каталог
- [ ] **3.1** Если тариф в продаже, он показывается клиенту в списке тарифов.
- [ ] **3.2** Если тариф в архиве, он не показывается в списке тарифов, но доступен для продления подписки, у которой он сейчас, пока подписка активна.

#### Первая покупка
- [ ] **3.3** Если клиент без подписок выбрал тариф, он видит экран подтверждения: тариф, срок, цена, итог к оплате.
- [ ] **3.4** Если клиент нажал «Оплатить», создаётся счёт у провайдера на сумму с экрана подтверждения, и клиент переходит к оплате.
- [ ] **3.5** Если клиент дважды нажал «Оплатить» на одном экране подтверждения, создаётся один счёт.
- [ ] **3.6** Если провайдер подтвердил оплату, в панели создаётся ровно один пользователь с параметрами тарифа (срок, лимит устройств, сквады), подписка магазина связывается с ним, платёж переходит в «применён», клиент получает ссылку на подписку и инструкцию по подключению.
- [ ] **3.7** Если оператор изменил цену или параметры тарифа после создания счёта, применяются условия на момент создания счёта.
- [ ] **3.8** Если клиент не оплатил счёт за время его жизни, счёт истекает и подписка не создаётся.
- [ ] **3.9** Если провайдер подтвердил оплату по истёкшему счёту, подписка создаётся, как по действующему.
- [ ] **3.10** Если клиент создал новый счёт за ту же операцию (та же покупка или продление той же подписки), не оплатив старый, старый счёт отменяется в магазине (и у провайдера, если провайдер это поддерживает). Счета за другие операции не затрагиваются.
- [ ] **3.11** Если оплачены оба счёта одной покупки, первая применённая оплата создаёт подписку, а вторая продлевает её на срок своего тарифа; команда получает уведомление. Если оба счёта были с одним промокодом, скидку получают оба, превышение лимита активаций записывается в журнал.
- [ ] **3.12** Если провайдер отклонил оплату, клиент видит сообщение об этом и может попробовать снова; подписка не создаётся.
- [ ] **3.13** Если клиент заблокировал бот до сообщения об успехе, подписка всё равно создаётся, а недоставка записывается в журнал.
- [ ] **3.14** Первая подписка получает название по умолчанию.
- [ ] **3.15** Если новый клиент впервые открыл бот по реферальной ссылке, записывается реферальная связь. Если клиент уже существовал, ссылка ведёт на него самого или он усыновлён, связь не записывается.
- [ ] **3.16** Если у клиента есть триальная подписка, покупка применяется к ней: пользователь панели и ссылка прежние; оплаченный срок добавляется к оставшимся дням триала; лимит устройств и сквады устанавливаются по тарифу; лимит и стратегия сброса трафика — по тарифу, счётчик трафика обнуляется.
- [ ] **3.36** Если единственная подписка клиента — триальная, в её карточке вместо «Продлить» показывается «Купить подписку», а в главном меню — «Купить подписку»; кнопка ведёт к выбору тарифа, покупка применяется к триальной подписке (3.16).

#### Продление
- [ ] **3.17** Если подписка активна, новая дата окончания — прежняя дата окончания плюс срок тарифа.
- [ ] **3.18** Если подписка истекла, новая дата окончания — момент подтверждения оплаты плюс срок тарифа.
- [ ] **3.19** При продлении пользователь панели и ссылка подписки не меняются.
- [ ] **3.20** Если тариф подписки в архиве, а подписка активна, продление доступно по текущей цене тарифа.
- [ ] **3.21** Если подписка истекла, а её тариф в архиве, продление этим тарифом недоступно; клиент может выбрать любой тариф в продаже, и он применяется к этой же подписке.
- [ ] **3.22** Если подписка истекла, пока клиент платил, продление считается от момента подтверждения оплаты.
- [ ] **3.23** Если у клиента одна подписка, «Продлить» сразу ведёт к ней, без выбора подписки.
- [ ] **3.24** Если у клиента несколько подписок (например, после усыновления), каждая показывается отдельно со своим названием, а продление доступно с экрана конкретной подписки.
- [ ] **3.35** Если у подписки нет тарифа (усыновлённая без сопоставления), «Продлить» ведёт к выбору тарифа из тех, что в продаже. При первом применении тарифа к подписке магазин выставляет в панели сквады и лимит устройств по тарифу.

#### Состояния платежа
- [ ] **3.34** Платёж проходит состояния из раздела «Платёж» в [01-domain.md](01-domain.md); каждый переход записывается в журнал. Один платёж — один счёт у провайдера.

#### Отрезки срока (данные для v1)
- [ ] **3.25** Каждое применённое продление или покупка добавляет к подписке отрезок срока со стоимостью, равной фактически оплаченной сумме.
- [ ] **3.26** Срок триала добавляется отрезком нулевой стоимости.

#### Контракт провайдера
- [ ] **3.27** Сценарии покупки и продления работают с провайдером только через контракт: создать счёт, принять подтверждение оплаты, запросить статус счёта, отменить счёт, сообщить, в каких валютах провайдер принимает счёт. Подключение нового провайдера не требует изменений в сценариях.
- [ ] **3.28** Платёж считается оплаченным только после подтверждения провайдера, проверенного по правилам этого провайдера. Непроверенное подтверждение отклоняется и записывается в журнал.
- [ ] **3.29** Если подтверждение от провайдера не дошло, магазин узнаёт об оплате, периодически запрашивая статус незавершённых счетов: до истечения счёта и ещё 24 часа после.
- [ ] **3.30** Если провайдер недоступен при создании счёта, клиент видит сообщение «Оплата временно недоступна, попробуйте позже»; ничего не создаётся.
- [ ] **3.33** Счёт всегда выставляется в валюте учёта магазина. Провайдер, который её не принимает, недоступен для выбора, а админка показывает это при его подключении ([решение 0020](decisions/0020-currency.md)).

#### ЮКасса
- [ ] **3.31** ЮКасса реализована через контракт провайдера (3.27) и проходит критерии 3.4–3.12 и 3.28–3.30.
- [ ] **3.32** После оплаты клиент возвращается в бот.

### Блок 4. Надёжность: вебхуки, сверка, повтор операций, журнал
- **Версия:** MVP
- **Сценарии:** «Реакция на изменения в панели», «Повтор неудавшихся операций», «Разобрать платёж «оплачен, не применён»»; сквозные правила 1–4

#### Вебхуки панели
- [ ] **4.1** Если подпись вебхука неверна или отсутствует, событие отклоняется и записывается в журнал.
- [ ] **4.2** Если одно и то же событие пришло повторно, его эффект применяется один раз.
- [ ] **4.3** Если в панели увеличили дату окончания, магазин добавляет к подписке отрезок нулевой стоимости.
- [ ] **4.4** Если в панели уменьшили дату окончания, магазин срезает отрезки с конца.
- [ ] **4.5** Если в панели изменили лимиты или сквады, магазин принимает их как факт.
- [ ] **4.6** Если пользователя удалили в панели, подписка помечается удалённой: клиент её больше не видит, история платежей сохраняется, событие записано в журнал.
- [ ] **4.7** Если подписку отключили в панели, клиент видит «Подписка отключена, обратитесь в поддержку», кнопки «Продлить» нет, напоминания не отправляются. Магазин сам подписку не включает. Если оплата всё же пришла (счёт создан до отключения), она применяется к сроку, пользователь в панели остаётся отключённым, команда получает уведомление. Если подписку включили — клиент снова видит обычное состояние.
- [ ] **4.29** Если ссылку подписки отозвали в панели, магазин сохраняет новую ссылку и отправляет клиенту сообщение с новой ссылкой, кнопкой копирования и инструкцией. Страница-переходник продолжает работать: ссылка подставляется в момент перехода.

#### Сверка с панелью
- [ ] **4.8** Магазин периодически сверяет состояние всех подписок с панелью. Если вебхук не дошёл, расхождение обнаруживается при следующей сверке и исправляется по тем же правилам, что 4.3–4.7.
- [ ] **4.9** Журнал показывает, каким путём магазин узнал об изменении: вебхук или сверка.
- [ ] **4.10** Если событие обнаружено сверкой с опозданием, его последствия для клиента применяются, только если ещё актуальны.

#### Недоступность панели
- [ ] **4.11** Если панель недоступна, оплаты принимаются и остаются в состоянии «оплачен, не применён» до её восстановления.
- [ ] **4.12** Если панель недоступна, клиент видит последние известные данные с пометкой, что они могут быть неактуальны.
- [ ] **4.13** Если панель недоступна дольше заданного времени, команда получает уведомление.

#### Повтор операций
- [ ] **4.14** Любое изменение в панели (применение платежа, создание подписки, выдача дней, промокод на дни, смена даты при возврате, удаление устройств) выполняется как операция очереди. Если операция не выполнилась из-за ошибки, система повторяет её с нарастающими интервалами. Повторы прекращаются по первому из условий: истекло заданное время или исчерпано предельное число попыток.
- [ ] **4.15** Повтор не даёт двойного эффекта. Перед внешним действием операция сверяет текущее состояние (например, не создан ли уже пользователь в панели).
- [ ] **4.16** Незавершённые операции продолжаются после перезапуска магазина.
- [ ] **4.17** Операции над одной подпиской применяются строго в том порядке, в котором возникли, в том числе если они ставятся одновременно из разных мест.
- [ ] **4.18** Каждая попытка записывается в журнал. Попытка засчитывается до выполнения: операция, которая раз за разом обрывает выполнение (например, роняет процесс), доходит до лимита попыток и становится проваленной, а не перезапускается бесконечно.
- [ ] **4.27** Если операция над подпиской окончательно провалилась, следующие операции этой подписки не выполняются, пока команда её не разберёт; в «Требуют внимания» видно, сколько операций ждёт за проваленной. Операции других подписок выполняются как обычно.
- [ ] **4.28** Большая работа (например, рассылка) выполняется множеством небольших операций, а не одной долгой.

#### «Оплачен, не применён»
- [ ] **4.19** Если платёж оплачен, но не применён сразу, клиент получает сообщение «Оплата получена, подписка создаётся».
- [ ] **4.20** Если автоматические попытки исчерпаны, платёж появляется в списке «Требуют внимания», на главной странице админки виден счётчик, команда получает уведомление.
- [ ] **4.21** Карточка такого платежа показывает клиента, что должно было примениться, историю попыток и текст ошибки.
- [ ] **4.22** Участник команды может применить платёж повторно, применить его созданием новой подписки или отметить решённым вручную. Отметка вручную требует комментария и переводит платёж в состояние «решён вручную»; клиент получает нейтральное уведомление, комментарий виден только команде.
- [ ] **4.23** Если провайдер прислал подтверждение оплаты, которой магазин не знает, она появляется в «Требуют внимания» с пометкой «неизвестный платёж», команда получает уведомление. Команда может привязать платёж к клиенту и выбрать, что применить (покупка или продление), отметить решённым вручную или вернуть деньги (владелец).
- [ ] **4.24** После решения клиент получает уведомление о результате.

#### Журнал
- [ ] **4.25** Каждое изменение подписки и платежа и каждое ручное действие команды записывается в журнал: кто (участник команды, клиент, система, панель или провайдер), что, когда, над чем, с каким результатом.
- [ ] **4.26** Записи журнала нельзя изменить или удалить через админку.

### Блок 5. Триал и реестр устройств
- **Версия:** MVP
- **Сценарии:** «Триал»; решение 0013
- **Вне блока:** отзыв триала по устройству, чёрные списки (v1); подписка на канал, точка расширения проверок (потом)

#### Триал
- [ ] **5.1** Владелец включает или выключает триал и задаёт его параметры: срок, лимит трафика (0 — без ограничения), лимит устройств, сквады. Стратегия сброса трафика триала — «не сбрасывать»: лимит действует на весь пробный период.
- [ ] **5.2** Если триал включён и доступен клиенту, предложение «Попробовать бесплатно» показывается в главном меню и внизу экрана выбора тарифа.
- [ ] **5.3** Триал недоступен, и предложение не показывается, если клиент уже получал триал, хотя бы раз платил или усыновлён.
- [ ] **5.4** Если клиент нажал «Попробовать бесплатно», в панели создаётся пользователь с параметрами триала, клиент получает ссылку и инструкцию, факт использования триала закрепляется за клиентом.
- [ ] **5.5** Повторное нажатие не создаёт второй триал.
- [ ] **5.6** Если панель недоступна, клиент получает «Подписка создаётся», создание повторяется (4.14). Триал считается выданным после создания пользователя в панели.

#### Реестр устройств
- [ ] **5.7** Когда панель сообщает о подключении устройства к любой подписке, магазин записывает в реестр: HWID, клиента, подписку, дату подключения.
- [ ] **5.8** Если событие о подключении к триальной подписке не дошло, устройство попадает в реестр при сверке: для триальных подписок сверка запрашивает список устройств пользователя. Для остальных подписок реестр ведётся по событиям панели.
- [ ] **5.9** Удаление устройства клиентом или в панели не удаляет запись из реестра.
- [ ] **5.10** Если трафик триала исчерпан (событие панели), клиент получает «Трафик пробного периода закончился» с кнопкой «Купить подписку».

### Блок 6. Управление устройствами
- **Версия:** MVP
- **Сценарии:** «Управление устройствами»
- **Вне блока:** ограничение числа удалений (потом)

- [ ] **6.1** Раздел «Устройства» показывается в подписке, только если в панели включён лимит устройств.
- [ ] **6.2** Раздел показывает устройства подписки — платформа, модель, приложение, дата подключения — и сколько мест занято из доступных; лимит берётся из панели.
- [ ] **6.3** Список читается из панели при открытии раздела.
- [ ] **6.4** Если клиент удалил устройство, оно удаляется в панели, список обновляется, действие записывается в журнал.
- [ ] **6.5** Удаление всех устройств сразу требует подтверждения.
- [ ] **6.6** Если панель недоступна, удаление ставится в повтор (4.14), клиент видит, что устройство будет удалено, как только панель станет доступна.
- [ ] **6.7** Если у клиента несколько подписок, устройства показываются для каждой отдельно.

### Блок 7. Напоминания
- **Версия:** MVP
- **Сценарии:** «Истечение подписки и напоминания»; решение 0014
- **Вне блока:** уведомления о трафике, помощь с подключением (v1)

#### Расписание
- [ ] **7.1** Владелец задаёт расписание напоминаний для платных подписок — список смещений в часах до и после окончания. По умолчанию: за 72 часа, за 24 часа, через 72 часа после.
- [ ] **7.2** Для триала задаётся отдельное расписание; по умолчанию — за 24 часа. Напоминание триала использует свой текст.
- [ ] **7.3** Изменение расписания применяется без перезапуска; запланированные напоминания пересчитываются.

#### Планирование и отправка
- [ ] **7.4** Для каждой подписки момент отправки каждого напоминания — дата окончания минус смещение.
- [ ] **7.5** Когда момент наступил, клиент получает напоминание с названием подписки, датой окончания и кнопкой «Продлить», которая ведёт к продлению именно этой подписки.
- [ ] **7.6** Перед отправкой магазин сверяет дату окончания с панелью. Если дата отличается, напоминание не отправляется, а расписание пересчитывается. Если панель недоступна, напоминание откладывается до её восстановления; если за это время наступило следующее, отправляется только самое позднее.
- [ ] **7.7** Если магазин был недоступен, после запуска досылаются наступившие и неотправленные напоминания; если наступили несколько по одной подписке, отправляется только самое позднее.
- [ ] **7.8** Каждое напоминание отправляется не больше одного раза: если оно уже отправлено и дата окончания не изменилась, повторно оно не отправляется, в том числе после сбоя в момент отправки.
- [ ] **7.9** Если дата окончания изменилась (продление, правка в панели), напоминания планируются заново от новой даты.
- [ ] **7.10** У каждой подписки свои напоминания.

#### Содержание
- [ ] **7.11** Если тариф подписки в архиве, напоминание до окончания сообщает, что продлить этот тариф можно только пока подписка активна, а после окончания нужно будет выбрать новый.
- [ ] **7.12** Когда подписка истекла (событие панели или сверка), клиент получает «Подписка истекла» с кнопкой «Продлить» — если подписку к этому моменту не продлили.
- [ ] **7.13** По окончании триала клиент получает одно сообщение — предложение купить подписку (без «Подписка истекла» и напоминания в момент окончания); покупка применяется к триальной подписке (3.16).
- [ ] **7.15** Если напоминание платной подписки совпадает с моментом окончания, отправляется только «Подписка истекла» (7.12).
- [ ] **7.16** Отключённой в панели подписке напоминания не отправляются (4.7).
- [ ] **7.14** Недоставленное напоминание записывается в журнал и повторно не отправляется.

### Блок 8. Промокоды
- **Версия:** MVP
- **Сценарии:** «Промокод»
- **Вне блока:** фиксированная скидка, промокоды на бонусы (v1)

#### Создание
- [ ] **8.1** Владелец создаёт промокод: код (вводит сам или генерирует), вид — скидка в процентах или дни, значение. Скидка — от 1 до 100%.
- [ ] **8.2** Владелец может задать ограничения: срок действия, общее число активаций, только для клиентов без оплат, только для выбранных тарифов (для скидки). Одна активация на клиента действует всегда.
- [ ] **8.3** Владелец видит число активаций промокода и может отключить его. Отключённый промокод ведёт себя как несуществующий.

#### Скидка
- [ ] **8.4** На экране подтверждения покупки или продления клиент может ввести промокод; итог пересчитывается и показывается до оплаты.
- [ ] **8.5** К одному платежу применяется не больше одного промокода.
- [ ] **8.6** Активация засчитывается при применении платежа. Если клиент не оплатил, активация не расходуется.
- [ ] **8.7** Если промокод истёк, исчерпался или был отключён, пока клиент платил, клиент получает скидку, которую видел (3.7).
- [ ] **8.8** При скидке 100% итог нулевой: создаётся платёж с нулевой суммой без счёта у провайдера, подписка создаётся или продлевается сразу. Такой платёж считается покупкой (триал после него недоступен, клиент больше не «без оплат») и добавляет к выручке ноль.
- [ ] **8.9** Если на экране подтверждения ввести промокод на дни, клиент видит подсказку, что такой код активируется в меню.

#### Дни
- [ ] **8.10** Клиент вводит промокод на дни через «Ввести промокод» в меню. Дни добавляются к подписке отрезком нулевой стоимости, в том числе к триальной; если подписок несколько, клиент выбирает, к какой; если подписка истекла, дни отсчитываются от момента активации.
- [ ] **8.11** Если у клиента нет подписок, промокод на дни не активируется, клиент видит, что код добавляет дни к подписке и сначала её нужно оформить.

#### Ошибки и защита
- [ ] **8.12** Если код не существует, истёк, исчерпан, уже использован клиентом, не подходит к тарифу или доступен только клиентам без оплат, клиент видит соответствующую причину и может продолжить без промокода.
- [ ] **8.13** После нескольких неверных кодов подряд ввод промокодов для клиента временно ограничивается.
- [ ] **8.14** Каждая активация записывается в журнал.

### Блок 9. Миграция
- **Версия:** MVP
- **Сценарии:** «Первое открытие бота усыновлённым клиентом»; [05-migration.md](05-migration.md); решения 0002, 0012
- **Вне блока:** адаптер Bedolaga, привязка по ссылке подписки, раздел «Пользователи панели без клиента» (v1)

#### Усыновление
- [ ] **9.1** Владелец запускает усыновление из админки. Сначала всегда выполняется пробный прогон.
- [ ] **9.2** Отчёт пробного прогона показывает: сколько пользователей панели будет усыновлено, сколько получится клиентов, сколько клиентов с несколькими подписками, у скольких пользователей нет Telegram ID (они продолжают работать в панели, но к клиентам не привязываются), сколько уже усыновлено ранее; сколько подписок сопоставилось с каждым тарифом, сколько осталось «без тарифа» и у скольких параметры в панели отличаются от тарифа.
- [ ] **9.3** Применить усыновление можно только после пробного прогона. Применение идёт по тем же правилам; по его итогам показывается итоговый отчёт.
- [ ] **9.4** Пользователи панели с одним Telegram ID становятся одним клиентом с несколькими подписками.
- [ ] **9.5** Срок усыновлённой подписки — отрезок нулевой стоимости. Клиент помечается усыновлённым.
- [ ] **9.6** Усыновление ничего не меняет в панели.
- [ ] **9.7** Повторный запуск не создаёт дублей: уже усыновлённые пользователи пропускаются.
- [ ] **9.15** В пробном прогоне оператор задаёт сопоставление «сквады и лимит устройств → тариф». Сопоставленная подписка получает тариф; остальные — пометку «без тарифа».
- [ ] **9.16** Подписки называются «Основная», «Подписка 2», «Подписка 3» в порядке создания пользователей в панели.

#### Импорт
- [ ] **9.8** Промежуточный формат описан в [migration-format.md](migration-format.md) как публичный контракт с номером версии.
- [ ] **9.9** Адаптер remnawave-tg-shop — отдельная команда: читает базу старого бота по подключению только на чтение и формирует файл в промежуточном формате — как для оригинального remnawave-tg-shop, так и для форка автора.
- [ ] **9.10** Импорт принимает файл в промежуточном формате и включает усыновление: пользователи панели, связанные в файле, и пользователи панели, которых в файле нет, усыновляются в том же прогоне.
- [ ] **9.17** Клиент из файла без пользователя в панели становится обычным клиентом, не усыновлённым. Если в файле отмечено, что он использовал триал, триал ему недоступен.
- [ ] **9.11** Отчёт пробного прогона импорта дополнительно показывает: сколько связей с пользователями панели найдено и не найдено, сколько реферальных связей и кодов перенесётся, что не распознано, какие конфликты есть.
- [ ] **9.12** Если пользователь панели из файла уже привязан к другому клиенту, это конфликт: он показывается в отчёте и не применяется.
- [ ] **9.13** Если клиент открыл бот по реферальной ссылке старого бота, она распознаётся по перенесённому коду. Для нового клиента записывается реферальная связь (3.15).
- [ ] **9.14** Каждое усыновление и импорт записываются в журнал.

### Блок 10. Карточка клиента, выдача дней, возврат вручную
- **Версия:** MVP
- **Сценарии:** «Найти клиента и продлить», «Вернуть деньги»
- **Вне блока:** возврат через API провайдера и на бонусный счёт, быстрые действия в боте, сообщение клиенту из карточки (v1)

#### Поиск и карточка
- [ ] **10.1** Клиента можно найти по Telegram ID, username, имени, ссылке подписки или имени пользователя в панели.
- [ ] **10.2** Карточка клиента показывает: подписки с состоянием из панели (тариф, срок, статус), устройства, платежи, триал, реферальные связи (кто пригласил, кого пригласил), пометки «бот заблокирован» и «усыновлён», журнал действий по клиенту.

#### Действия
- [ ] **10.3** Участник команды выдаёт дни: выбирает подписку, число дней и пишет обязательный комментарий. Дни добавляются в панели и отрезком нулевой стоимости в магазине; если подписка истекла, дни отсчитываются от момента выдачи.
- [ ] **10.4** Клиент получает уведомление «К подписке [название] добавлено N дней». Комментарий виден только команде.
- [ ] **10.5** Участник команды может сбросить устройства подписки и немедленно пересинхронизировать подписку с панелью.
- [ ] **10.6** Участник команды фиксирует запрос клиента на возврат — запись с комментарием в карточке. Запрос закрывается возвратом или отказом с комментарием; клиент получает уведомление о результате.
- [ ] **10.7** Каждое действие записывается в журнал с указанием участника и комментария.

#### Возврат вручную
- [ ] **10.8** Владелец выбирает платёж и нажимает «Вернуть». Система предлагает сумму — неиспользованную стоимость этого платежа по модели отрезков. Владелец может изменить сумму, но не больше заплаченного.
- [ ] **10.9** Срок подписки сокращается на неиспользованную часть возвращаемого платежа независимо от суммы: будущий отрезок убирается целиком, текущий обрезается по текущий момент, полностью использованный не меняется.
- [ ] **10.10** Экран подтверждения показывает сумму и новую дату окончания подписки (или что подписка закончится сейчас).
- [ ] **10.11** Владелец возвращает деньги сам и отмечает возврат как выполненный вручную. Магазин меняет дату окончания в панели, клиент получает уведомление, действие записывается в журнал.
- [ ] **10.12** По платежу возможен один возврат — полный или на меньшую сумму. После него платёж в состоянии «возвращён» или «частично возвращён», повторный возврат недоступен.
- [ ] **10.13** Подписка, которую закрыл полный возврат, не получает напоминаний об окончании и сообщения «Подписка истекла».

### Блок 11. Рассылка
- **Версия:** MVP
- **Сценарии:** «Рассылка»
- **Вне блока:** остальные сегменты, отключение рассылок клиентом, отложенные рассылки (v1 и позже)

#### Создание
- [ ] **11.1** Владелец создаёт рассылку: текст с форматированием, при желании одно изображение и кнопки «Купить», «Продлить» или ссылка.
- [ ] **11.2** Сегменты в MVP: все клиенты; с активной подпиской; с истёкшей подпиской. При выборе сегмента показывается число получателей.
- [ ] **11.3** Владелец может отправить тестовое сообщение себе.
- [ ] **11.4** Перед отправкой владелец подтверждает рассылку, видя число получателей. Состав получателей фиксируется в момент подтверждения.

#### Отправка
- [ ] **11.5** Рассылка идёт с учётом ограничений Telegram. Владелец видит прогресс.
- [ ] **11.6** Каждый получатель получает сообщение не больше одного раза; после перезапуска магазина рассылка продолжается с места остановки. Сообщение, отправка которого оборвалась сбоем, повторно не отправляется.
- [ ] **11.7** Идущую рассылку можно остановить; оставшимся получателям сообщение не отправляется.
- [ ] **11.8** Итог рассылки: доставлено, бот заблокирован, ошибки. История рассылок с итогами доступна в админке.
- [ ] **11.9** Если клиент заблокировал бот, он получает пометку «бот заблокирован»; пометка снимается, когда клиент снова открывает бот.
- [ ] **11.10** Кнопка «Продлить» ведёт к продлению (с выбором подписки, если их несколько), а у клиента без подписок — к выбору тарифа; «Купить» — к выбору тарифа.
- [ ] **11.11** Каждая рассылка записывается в журнал.

### Блок 12. Инструкция по подключению и страница-переходник
- **Версия:** MVP
- **Сценарии:** события С1, С2, С3 в [03-screens.md](03-screens.md); [решение 0019](decisions/0019-subpage-guide.md)

#### Инструкция
- [ ] **12.1** Инструкция собирается из конфига Subscription Page, назначенного подписке в панели: через внешний сквад пользователя, а если он не задан — из конфига по умолчанию.
- [ ] **12.2** Тексты берутся на языке клиента; если его нет в конфиге — на языке бота по умолчанию; если нет и его — на первом языке конфига.
- [ ] **12.3** Платформы показываются сворачиваемыми блоками. Внутри — рекомендуемое приложение и его шаги; остальные приложения платформы — по кнопке «Другие приложения».
- [ ] **12.4** Кнопки шагов: копирование — копирует ссылку на подписку; внешняя ссылка — обычная ссылка; импорт в приложение — через страницу-переходник.
- [ ] **12.5** SVG-иконки и брендинг веб-страницы из конфига в боте не используются.
- [ ] **12.6** Кнопка «Открыть в браузере» ведёт на ссылку подписки.
- [ ] **12.7** Магазин хранит последний полученный конфиг и периодически обновляет его. В админке есть кнопка «Обновить сейчас».
- [ ] **12.8** Если панель недоступна, используется последний сохранённый конфиг. Если конфиг ещё ни разу не был получен, клиент видит `guide.unavailable` с кнопками «Скопировать ссылку» и «Открыть в браузере».
- [ ] **12.9** Своих полей инструкции в админке магазина нет.

#### Страница-переходник
- [ ] **12.10** Кнопка импорта ведёт на страницу магазина с непрозрачным токеном. Диплинк собирается на сервере магазина из конфига и ссылки подписки. Произвольный адрес перенаправления страница не принимает.
- [ ] **12.11** Ссылка на подписку не попадает в адрес страницы-переходника.
- [ ] **12.12** Страница автоматически открывает приложение и показывает кнопку на случай, если это не сработало, а также ссылки на установку приложения из конфига.
- [ ] **12.13** Страница показывается на языке клиента и в теме его устройства.
- [ ] **12.14** Если подписка удалена или токен недействителен, страница показывает `redirect.invalid`.
