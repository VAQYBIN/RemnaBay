# Открытые вопросы

## Объём
- [ ] **Функции Bedolaga, которыми реально пользуются.** Нужно к объёму v1, чтобы не гнаться за паритетом.

## Роли и сущности
- [ ] **Передача подписки и делегирование.** Передача подписки другому клиенту; доступ «владелец платит, пользователь подписки видит её у себя». Не в MVP — решить, когда и нужно ли вообще.

## Сценарии
- [ ] **Автопродление.** Нужно ли и когда: сохранённые карты у провайдеров или что-то ещё. В MVP не входит, записано в [backlog.md](backlog.md).
- [ ] **Блокировка клиентов в целом.** Нужна ли возможность заблокировать клиента полностью (не только триал) и что тогда происходит с его оплаченными подписками?
- [ ] **Внешние чёрные списки из коробки.** Какие списки сообщества подключать по умолчанию и в каком формате их читать?

## К планированию v1
- [ ] **Без чего автор не готов переезжать.** Решить для v1: блокировка клиентов, автопродление и другое из текущего магазина автора ([решение 0031](decisions/0031-stages-refined.md)).

## Миграция
- [ ] **Массовое начисление бонусов при миграции.** Нужен ли инструмент «начислить бонус всем усыновлённым клиентам», или достаточно ручного начисления?

## Проверить на реальных данных
Первые задачи после разрешения начать код — до реализации соответствующих блоков.
- [ ] Ограничения rich-сообщений: число кнопок и объём текста — хватит ли их для инструкции с несколькими платформами.
- [ ] Как чужие боты хранят несколько подписок с одним Telegram ID (важно для адаптеров миграции).
- [ ] Можно ли в «живом меню» редактировать обычное сообщение в rich и обратно — на этом держится принцип «меню в одном сообщении» (0017).
- [ ] Показывается ли date_time в часовом поясе клиента.
- [ ] Как rich-сообщения выглядят в старых версиях клиентов, на десктопе и в вебе.

## Реализация
- [ ] **Автоматический перезапуск по проверке здоровья.** [Решение 0026](decisions/0026-deployment.md) обещает «проверки здоровья веба и воркера для автоматического перезапуска», но Docker Compose сам не перезапускает контейнер в состоянии unhealthy — только упавший. Варианты: процесс сам завершается, когда потерял работоспособность, и поднимается через `restart: unless-stopped`; или отдельный сервис-перезапускатель (лишний сервис в compose). Решить к этапу 11. Появилось на этапе 0.
- [ ] **Генератор клиента админки из OpenAPI.** Решения 0022 и 0025 требуют генерировать клиент админки из OpenAPI-схемы FastAPI, но инструмент в [решении 0027](decisions/0027-versions.md) не выбран. Нужен к этапу 4. Появилось на этапе 0.
- [ ] **Документация API в рабочем режиме.** FastAPI по умолчанию отдаёт `/docs`, `/redoc` и `/openapi.json` всем, кто откроет адрес магазина: при проверке через ngrok схема API была видна снаружи. Закрывать ли их в рабочем режиме (оставив для разработки), а схему для генерации клиента админки получать при сборке? Решить на этапе 4 вместе с путями ([решение 0026](decisions/0026-deployment.md): «один домен с фиксированными путями»). Появилось на этапе 0.

- [ ] **Права API-токена магазина.** В панели 3.4.4 токен по умолчанию получает скоуп `*` — доступ ко всему API, включая массовые действия над всеми пользователями (`users:bulk-all-*`, `external-squads:add-users`). Скоупы можно сузить до отдельных запросов. Давать ли оператору список минимальных скоупов для магазина в документации и проверять ли права токена при подключении (1.8)? Нужен к этапу 2 (клиент панели). Появилось на этапе 1, см. [research/spike-panel.md](research/spike-panel.md).

- [ ] **Кнопка «Открыть в браузере» до первого ответа панели.** По 12.16 магазин узнаёт у панели, пускает ли она браузер на страницу подписки, вместе с конфигом. Если конфиг и ответ ещё ни разу не были получены (панель недоступна с самого подключения), показывать ли кнопку «Открыть в браузере» и какой текст — `guide.unavailable` или `guide.unavailable_no_browser`? Нужен к блоку 12. Появилось на этапе 1, [решение 0043](decisions/0043-panel-checks-refinements.md).
