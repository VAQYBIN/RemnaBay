# Правила для ИИ-агентов

## Стадия проекта
Проект находится на стадии **проектирования**. Код не пишется, стек не выбирается, структура приложения не закладывается, пока не выполнены **все** условия:

1. Слои спеки 0–6 утверждены для MVP, включая экраны (`docs/03-screens.md`) и настройки (`docs/04-operator-settings.md`).
2. Стек зафиксирован решениями в `docs/decisions/`.
3. Владелец провёл полное ревью спеки и явно разрешил начать код — это отмечено в чек-листе «Путь до кода» в `docs/README.md`.

Утверждённый объём MVP в `docs/06-scope.md` сам по себе **не** разрешает писать код.

Если тебя просят написать код, а условия не выполнены, — напомни об этом и спроси, точно ли это нужно сейчас.

### Исключение: исследовательские эксперименты
Эксперимент, который проверяет технический вопрос до принятия решения, разрешён, если:
- он описан в `docs/research/` (что проверяем и по каким вопросам);
- код лежит вне репозитория проекта или в папке `spikes/`, которая не входит в сборку;
- код **не переносится** в проект — переносится только вывод;
- выводы записываются в тот же файл в `docs/research/`, а решение — в `docs/decisions/`.

## Источник истины
- Спецификация в `docs/` — единственный источник истины о том, что делает продукт.
- Продуктовые решения принимает только владелец проекта. Агент их не принимает.
- Если в спеке нет ответа на вопрос — **не выдумывай**. Добавь вопрос в `docs/open-questions.md` и задай его владельцу.
- Если твоё предложение ещё не утверждено, помечай его явно: `> **Предложение (не утверждено):** ...`

## Работа с документацией
- Слои спеки идут по порядку (см. `docs/README.md`). Не заполняй следующий слой, пока предыдущий не утверждён, — если только об этом не попросили.
- Каждое принятое решение, которое влияет на продукт, записывается в `docs/decisions/` по шаблону `docs/decisions/template.md`.
- Используй термины из `docs/glossary.md`. Новый термин — сначала в глоссарий.
- Язык документации — русский.
- Не удаляй и не переписывай утверждённые разделы без прямой просьбы.

## Правила разработки
Действуют, когда в чек-листе «Путь до кода» (`docs/README.md`) отмечен пункт «Владелец разрешил начать код». Порядок работы — [`docs/plan.md`](docs/plan.md).

### Задача
- Задача — один этап плана или один блок из `docs/06-scope.md` с номерами его критериев. Всё, что в блоке помечено «Вне блока», не делается.
- Перед работой прочитай критерии блока, сценарии, на которые он ссылается, и решения из `docs/decisions/`, которые его касаются.
- Если для реализации не хватает ответа в спеке — не придумывай. Запиши вопрос в `docs/open-questions.md` и спроси владельца. Если без ответа можно продолжать остальную часть задачи — продолжай.
- Если реализация показала, что спека в чём-то неверна или противоречива, — не меняй поведение молча: опиши проблему и предложи правку спеки.
- Перед использованием API библиотеки сверяйся с её документацией через Context7, а не пиши по памяти (0040).

### Готовность
Задача готова, только когда:
- выполнены все критерии задачи;
- проходят `ruff`, `pyright` в строгом режиме и `pytest`; для админки — сборка и проверка типов TypeScript;
- для каждого критерия, который можно проверить автоматически, есть тест, и номер критерия указан в его описании;
- критерии, которые проверяются только руками, перечислены в отчёте с шагами проверки.

### Архитектурные правила (из решений)
- Панель — только через клиент панели (0028), фоновые задачи — только через интерфейс очереди (0024), оплата — только через контракт провайдера (3.27). Внутренности этих модулей остальной код не знает.
- Pydantic на всех границах: API, вебхуки, конфиг Subscription Page, промежуточный формат миграции, контракт провайдера (0022).
- Тексты бота — только по ключам (0018); строк, которые видит клиент, в коде нет.
- Сквозные правила из `docs/02-scenarios.md` обязательны везде: условия фиксируются при создании платежа, повтор не даёт двойного эффекта, перед внешним действием сверяется состояние, недоставка сообщения — не ошибка.
- Каждое изменение подписки и платежа и каждое ручное действие команды пишется в журнал (4.25).
- Модель данных из `docs/01-domain.md` реализуется целиком, даже если функции поверх неё отложены (0015).
- Схема базы меняется только миграциями Alembic; применённую миграцию не редактируют, а пишут новую.

### Зависимости и секреты
- Зависимости — только через uv (Python) и npm (админка), с lock-файлами (0027). Новая зависимость — с объяснением в отчёте; крупная — через решение.
- Секретов в коде и в репозитории нет. Все параметры `.env` — в `.env.example` с пояснениями.

### Язык
- Имена в коде (переменные, функции, классы, таблицы) — на английском.
- Комментарии, сообщения коммитов и отчёты — на русском, как и документация.

### Отчёт о выполненной задаче
- Какие критерии выполнены и чем это подтверждено (тесты, ручные шаги).
- Что не сделано и почему.
- Какие вопросы возникли и что записано в `docs/open-questions.md`.
- Какие предложения по правке спеки появились.

### Коммиты
- Небольшие, по смыслу; номера критериев — в сообщении коммита.
- Одна задача — одна ветка и один запрос на слияние.
